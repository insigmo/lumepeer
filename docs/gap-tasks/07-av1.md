# 07 — AV1

**Пункт бэклога:** 31. **Зависит от:** `06` (без согласования кодека
включать AV1 некуда). **Нужно:** машина с аппаратным AV1-энкодером —
Intel Arc / 12-е поколение и новее, NVIDIA 40-й серии, AMD RDNA3 — и вторая
машина как гость.

## Что уже есть (проверено по коду)

- `VideoCodec::Av1` **объявлен** в `crates/media/src/encode/mod.rs`, но
  `probe_hardware` отказывает ему на входе: `if config.codec !=
  VideoCodec::H264 { return None; }`. Оба аппаратных бэкенда
  (`windows.rs` — Media Foundation, `linux_vaapi.rs` — VA-API) отвечают
  `None` для AV1 **намеренно**: у AV1 другой профиль и другие буферы
  параметров, и переиспользовать H.264-ответ — это ровно тот дефект, ради
  которого §11 требует взаимной аппаратной поддержки.
- Комментарий в заголовке `encode/mod.rs`: «AV1 — опционально и только когда
  обе стороны имеют аппаратную поддержку; программного AV1 в v1 нет».
- `crates/media/src/encode/nv12.rs` — конвертация в NV12, общая.

## Задача 1 — проба

**Файл:** `crates/media/src/encode/mod.rs`

1. Сними безусловный отказ на входе `probe_hardware` и передай вопрос
   бэкендам: каждый отвечает **за свой** кодек и только после настоящей
   активации.
2. Программного AV1 нет — если аппаратной поддержки нет, ответ `None`, и
   `select_encoder` уходит на H.264. Никакого `libaom` в реальном времени.

## Задача 2 — Windows (Media Foundation)

**Файл:** `crates/media/src/encode/windows.rs`

`MFTEnumEx` с `MFT_ENUM_FLAG_HARDWARE` и подтипом `MFVideoFormat_AV1`;
активировать, скормить NV12, получить кадр — и только тогда `Hardware`.
Битрейт и запрос ключевого кадра — теми же свойствами MF, что у H.264.

## Задача 3 — Linux (VA-API)

**Файл:** `crates/media/src/encode/linux_vaapi.rs`

`VAProfileAV1Profile0` + `VAEntrypointEncSlice`; собственные буферы
параметров последовательности и кадра — **не переиспользовать
H.264-структуры**. Если профиль не поддерживается — честный `None`.

## Задача 4 — гость

**Файлы:** `apps/desktop/src/view-decoder.ts`, `apps/desktop/src/view-decoder.test.ts`

Строка конфигурации `VideoDecoder` для AV1 — `av01.0.05M.08` (Main, level 4.1,
8 бит) как стартовый профиль; таблица строк заведена пачкой `06`. Поддержку
спрашивать у браузера, не предполагать. Поток AV1 — это OBU, а не Annex-B:
проверь, что путь разбора кадров (`keyframe`-флаг берётся из заголовка чанка,
не из потока) от этого не зависит, и добавь тест.

## Задача 5 — фичи и релиз

Новых фич сборки, скорее всего, не нужно: AV1 идёт теми же
`encode-mf`/`encode-vaapi`. Если понадобилась новая — по образцу соседних,
не в `default`, плюс строки релизной матрицы.

## Чего НЕ делать

- Не тащить программный AV1-энкодер (`libaom`, `rav1e`, `SVT-AV1`) — ни как
  запасной путь, ни «для тестов на CI». Это прямое нарушение §11 и убьёт
  бюджет CPU (`ci/resource-budget.yml`).
- Не отвечать `Hardware` без реальной активации и одного закодированного
  кадра.
- Не делать AV1 предпочтительным по умолчанию, пока нет измерений: включать
  только при взаимной аппаратной поддержке, и решать по числам (задержка,
  битрейт при равном качестве), а не по громкости названия.
- Не трогать H.264-пути «заодно».

## Definition of done

- `cargo clippy -p lumepeer-media --all-targets --features encode-mf,encode-openh264 -- -D warnings` и та же команда с `encode-vaapi` — чисто.
- `cargo test --workspace` не хуже базового прогона.
- На машине с AV1-железом: `probe_hardware` возвращает `Hardware` для AV1,
  сессия согласует AV1, гость показывает картинку.
- На машине **без** AV1-железа: согласование даёт H.264, картинка есть,
  в логе видно почему.
- Замер: при одинаковом визуальном качестве зафиксировать битрейт AV1 против
  H.264 и задержку. Числа — в отчёт; без них включать AV1 по умолчанию
  нельзя.
