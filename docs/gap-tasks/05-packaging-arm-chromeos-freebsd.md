# 05 — Упаковка: ARM-устройства, ChromeOS, FreeBSD

**Пункт бэклога:** 10. **Зависит от:** ничего. **Нужно:** Raspberry Pi 4/5 с
64-битной Pi OS; Chromebook с включённым Linux (Crostini) — если его нет,
задача 2 закрывается частично, это отмечается в отчёте.

Здесь больше проверки и упаковки, чем кода. Смысл пачки — превратить «мы
собираем aarch64-deb» в «оно ставится и работает на настоящем устройстве».

## Что уже есть (проверено по коду)

- `.github/workflows/release.yml`, матрица `build`: шесть строк —
  linux amd64/arm64 (`.deb` и `.rpm` за один проход, `bundle.targets = "all"`),
  windows amd64/arm64, macos arm64/amd64. Фичи Linux:
  `capture-x11,capture-portal,encode-openh264`.
- ADR 0017 — минимальная glibc для Linux-сборок.
- ADR 0039 — Linux-клиент везёт оба типа сессии (X11 и портал) и своё аудио.
- Runtime-зависимости `.deb`/`.rpm`: `libpipewire-0.3-0`
  (`pipewire-libs` на RPM), рекомендуются `xdg-desktop-portal` и работающий
  `pipewire`.
- `Taskfile.yml` умеет кросс-сборку: `cross:linux-arm64`,
  `build:client:linux-arm64`, `sync:linux`, `remote:build:linux`.

## Задача 1 — Raspberry Pi (arm64)

**Файлы:** `docs/` (новый раздел), при необходимости `.github/workflows/release.yml`

1. Поставь текущий `aarch64` `.deb` на чистую 64-битную Pi OS. Зафиксируй
   всё, что не сошлось: версия glibc против ADR 0017, наличие
   `libwebkit2gtk-4.1`, `xdg-desktop-portal`, `pipewire`.
2. Прогони обе стороны: Pi как хост (X11-сессия и Wayland-сессия отдельно) и
   Pi как гость.
3. Программный `openh264` на Pi почти наверняка не вытянет 1080p60. Померяй
   и зафиксируй **числа**, а не ощущение: fps, задержка, загрузка CPU. Если
   упирается — правильный ответ здесь не «оптимизировать энкодер», а
   зафиксировать рекомендованный профиль (разрешение/fps) в документации.
   Аппаратный энкодер Pi (V4L2 M2M) — это отдельная задача, не эта.
4. Результат — раздел в `docs/` с проверенными требованиями и профилем.
   Обещать в README то, что не проверено, нельзя.
5. 32-битную Pi OS (armv7) **не поддерживаем**: новой строки в матрицу не
   добавлять, вместо этого записать отказ явно.

## Задача 2 — ChromeOS (Crostini)

**Файлы:** `docs/` (тот же раздел)

1. ChromeOS запускает Linux-приложения в контейнере Debian. Проверяй тот же
   `.deb` (amd64 или arm64 по устройству), никакой отдельной сборки.
2. Ключевые вопросы, ответы на которые надо получить экспериментом, а не
   рассуждением: видит ли Sommelier экран целиком (то есть можно ли быть
   **хостом** из контейнера — скорее всего нет, контейнер не видит рабочий
   стол ChromeOS), работает ли роль **гостя**, есть ли звук, работает ли
   ввод.
3. Ожидаемый честный итог: гость — да, хост — нет. Если так, это и записать,
   плюс закрыть путь в интерфейсе честным сообщением (§18), а не пустым
   экраном.

## Задача 3 — FreeBSD: разведка, не обещание

**Файлы:** `docs/adr/00NN-*.md` (новый ADR по итогам)

1. Проверь по факту: собирается ли `wry`/`webkit2gtk` из портов, есть ли
   `x11rb`-путь (должен работать), есть ли PipeWire.
2. Раннера FreeBSD в GitHub Actions нет — значит либо сборка в ВМ вручную,
   либо релизной строки не будет. Это решение, а не деталь: оформи ADR
   «FreeBSD не входит в поддерживаемые платформы» либо «входит как
   ручная сборка без релизных артефактов», с обоснованием из того, что
   реально получилось.
3. Не тратить сессию на доведение сборки до конца, если она упирается в
   зависимость, которой в портах нет. Зафиксировать, где именно упёрлось.

## Чего НЕ делать

- Не добавлять строки в релизную матрицу под платформы, которые нечем
  проверять: непроверенный артефакт хуже отсутствующего.
- Не менять фичи Linux-сборки (`capture-x11,capture-portal,encode-openh264`)
  ради одного устройства.
- Не браться за аппаратный энкодер Raspberry Pi (V4L2 M2M) — это отдельный
  бэкенд и отдельная пачка.
- Не понижать glibc-флор ADR 0017 без ADR.
- Не «чинить» производительность Pi изменением ABR-констант: они общие для
  всех платформ.

## Definition of done

- Раздел в `docs/` с проверенными требованиями и профилями для Pi и (если
  было устройство) ChromeOS: что работает, что нет, с числами.
- ADR по FreeBSD с явным решением.
- Если матрица менялась — релизная сборка зелёная на всех шести строках.
- `cargo clippy --workspace --all-targets -- -D warnings` и
  `cargo test --workspace` не хуже базового прогона.
- В отчёте отдельным списком: что проверить не удалось и какого железа не
  хватило.
