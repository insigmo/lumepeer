# 25 — Доступ до входа в систему: фундамент

**Пункт бэклога:** 11 (первая половина). **Зависит от:** `24`.
**Нужно:** Windows-машина, которую не жалко перезагружать и на которой можно
ставить и снимать службу; вторая машина как гость.

Самая большая и самая опасная пачка списка. Она вводит процесс с правами
SYSTEM, который держит сеть. Всё, что здесь написано про границы, важнее
того, что написано про функциональность.

## Что уже есть (проверено по коду)

- `crates/service/` — привилегированная служба `LumepeerHelper`
  (ADR 0043, 0049): `main.rs` (сама служба), `windows_service.rs`,
  `install.rs`, `client.rs` (клиентская половина: открывает канал и пишет
  **два байта**, привилегий не держит), `frame.rs` (чтение shared-memory
  отображения), `secure_desktop.rs`, `secure_desktop_input.rs`,
  `secure_desktop_launch.rs`.
- Приём, который уже работает и который здесь надо обобщить: служба
  **перезапускает саму себя** с аргументом `SECURE_DESKTOP_WORKER_ARG` в
  `Winsta0\Winlogon`, воркер снимает один кадр в общее отображение и
  выходит; для ввода — `SECURE_DESKTOP_INPUT_WORKER_ARG` с четырьмя
  проверенными числами в командной строке (ADR 0056, 0057).
- Служба регистрируется при установке (`installer-hooks.nsh`) и снимается
  деинсталлятором; `service_control::ensure_installed` вызывается на старте
  клиента (ADR 0063).
- Клиент на Windows и так запускается с `requireAdministrator`
  (`apps/desktop/src-tauri/build.rs`, ADR 0057).
- `apps/desktop/src-tauri/src/autostart.rs` прямо говорит, что запуск до
  входа — это **не** его задача.
- README, раздел «Written but not wired»: нужен процесс в сессии 0,
  раздающий захват и ввод в ту сессию, которая существует. Его нет.

## Задача 1 — ADR: где теперь граница доверия

Без этого ADR код писать нельзя. В нём обязаны быть ответы:

1. **Что именно переезжает в SYSTEM.** Рекомендуемое разделение: сеть,
   рукопожатие, согласие и гранты остаются в `crates/core` и живут в
   процессе службы; захват и ввод выполняет **агент** — обычный процесс,
   запущенный службой в активной пользовательской сессии. Служба не рисует
   пикселей и не жмёт клавиш сама.
2. **Кто разрешает вход, когда за машиной никого нет.** Ответ может быть
   только один: unattended-доступ (ADR 0033) — пароль устройства и
   опциональный TOTP, адресная книга как ворота (ADR 0034). Никаких
   «разрешить всем, раз некому спросить».
3. **Как соблюдается «нет скрытого захвата», когда некому смотреть на
   баннер.** Предложение: событие в аудит на каждый вход без человека, и
   неснимаемый баннер, который появляется в тот момент, когда кто-то входит
   в систему при живой сессии. Формулировку согласовать с ADR 0033.
4. **Что делает эта служба, когда клиент запущен обычным образом.** Два
   хоста на одной машине недопустимы: либо служба, либо пользовательский
   клиент, и переход между ними явный.

## Задача 2 — агент в пользовательской сессии

**Файлы:** `crates/service/src/` (новые модули), `crates/media`

1. Служба определяет активную консольную сессию
   (`WTSGetActiveConsoleSessionId`), получает её токен
   (`WTSQueryUserToken`) и запускает агент через `CreateProcessAsUser` — тот
   же приём, что уже используется для воркеров secure desktop, только
   агент живёт всю сессию, а не один кадр.
2. Канал служба ↔ агент: shared memory для кадров (образец — `frame.rs`) и
   именованный канал с DACL для команд. Формат — фиксированный, с проверкой
   длин; агент не доверяет службе больше, чем нужно, и наоборот.
3. Агент умирает вместе со своей сессией; служба это замечает и не
   притворяется, что картинка есть.
4. Ни одного пути, по которому агент может расширить грант: он исполняет уже
   авторизованное, как сегодняшний `InputInjector`.

## Задача 3 — сеть в службе

**Файлы:** `crates/service/src/`, `apps/desktop/src-tauri/src/network.rs`

1. Актор (сегодня — 8500 строк в `network.rs`, завязанных на Tauri) должен
   уметь работать без окна. Это главная инженерная работа пачки: выделить
   часть, не зависящую от Tauri, в переиспользуемый модуль. См. пачку `27`
   — она решает ту же задачу для мобильных клиентов; если `27` уже сделана,
   переиспользуй её результат, а не делай второй раз.
2. Хранилища (`ActorStores`) в службе указывают на машинные пути, а не на
   профиль пользователя. Права на эти файлы — только SYSTEM и
   администраторы: там ключи и хеш пароля устройства.
3. Keystore в SYSTEM — отдельный вопрос: `crates/net/src/keystore.rs`
   рассчитан на пользовательский keyring. Решить явно и записать в ADR
   (вариант: зашифрованный файл с DPAPI-машинным ключом).

## Чего НЕ делать

- Не давать службе третью «универсальную» операцию: каждая возможность
  привилегированной стороны перечислена и обоснована (ADR 0043).
- Не запускать webview и вообще UI в сессии 0.
- Не позволять работать одновременно службе-хосту и пользовательскому
  клиенту-хосту.
- Не ослаблять unattended: без пароля устройства входа нет.
- Не браться здесь за экран входа и смену сессий — это пачка `26`.
- Не переносить на службу Linux и macOS: там свои механизмы и своя пачка.

## Definition of done

- ADR со всеми четырьмя ответами.
- `cargo clippy --workspace --all-targets -- -D warnings` — чисто.
- `cargo test --workspace` не хуже базового прогона; новые тесты — на разбор
  сообщений канала служба↔агент и на отказ при отсутствии unattended.
- На настоящей машине: гость подключается к хосту, где сессия принадлежит
  службе; агент запускается в пользовательской сессии; картинка и ввод
  работают; выход пользователя из системы гасит агент, и гость видит честное
  состояние, а не замерший кадр.
- Проверено, что запустить второй хост (пользовательский клиент) при живой
  службе нельзя.
- Права на машинные файлы хранилищ проверены.
