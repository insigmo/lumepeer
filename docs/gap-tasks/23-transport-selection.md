# 23 — Выбор транспорта, откат и диагностика

**Пункт бэклога:** 51. **Зависит от:** `21`, `22`. **Нужно:** две машины за
разными NAT; желательно сеть, где QUIC/UDP режется (мобильный оператор,
корпоративный Wi-Fi) — иначе главный сценарий не проверить.

## Что уже есть (проверено по коду)

- Существующий путь: `PeerEndpoint` поверх iroh; `path_of(connection)` в
  `apps/desktop/src-tauri/src/network.rs` (~стр. 270) уже различает прямой
  путь и relay и достаёт регион relay (`relay_region`).
- Панель качества соединения: `apps/desktop/src/connection-quality.ts`,
  команда `connection_stats`.
- Повтор набора: 5 попыток с джиттером (ADR 0050) — расширены после
  «connection ended before it was accepted» на v0.0.45.
- Обфусцированный путь и его флаг — пачка `21`; пробой — пачка `22`.
- Известный факт: relay у iroh — это TCP+WS, а прямой путь уже UDP;
  «разрыв ~30 с» без keep-alive — это idle-timeout, а не DPI. Не строить
  логику выбора на этом заблуждении.

## Задача 1 — правило выбора

**Файл:** `apps/desktop/src-tauri/src/network.rs`

1. Порядок попыток задаётся **одним** местом в коде и описывается в ADR:
   например, iroh-прямой → обфусцированный → iroh-relay. Порядок — решение,
   а не то, что получилось из порядка написания веток.
2. Бюджеты времени на каждую попытку — константы, не литералы. Общий бюджет
   набора не должен вырасти: пользователь ждёт столько же, сколько сейчас.
3. Откат срабатывает **до** согласия: гость не должен видеть диалог,
   который потом отменится сменой транспорта.
4. Успешный транспорт запоминается для этого устройства и в следующий раз
   пробуется первым (`connection_history` уже существует; путь на диск — по
   правилу `ActorStores`).

## Задача 2 — переключение на живой сессии

Транспорт **не** меняется посреди сессии. Если соединение упало, действует
существующее окно переподключения (`crates/net/src/reconnect.rs`, тот же
`NodeId`, тот же `session_id`, неизменные гранты) — и вот при
переподключении выбор транспорта делается заново. Это надо явно описать и
покрыть тестом: смена транспорта не должна выглядеть как новая сессия и не
должна ничего расширять.

## Задача 3 — диагностика

**Файлы:** `apps/desktop/src/connection-quality.ts`, `apps/desktop/src/i18n.ts`

1. В панели видно: какой транспорт используется, прямой путь или relay,
   и — если был откат — какая попытка не удалась и почему.
2. Формулировки для человека, а не коды: «прямое соединение», «через
   ретранслятор», «обфусцированное прямое». Технические детали — в лог.
3. Все новые строки — во все локали.

## Задача 4 — проверка в сети, которая режет

1. Прогони соединение в сети, где UDP/QUIC ограничен. Зафиксируй: сколько
   времени занял откат, какой путь победил, сколько попыток ушло впустую.
2. Если обфусцированный путь не даёт выигрыша ни в одной доступной сети —
   это результат, и его надо записать: держать выключенным по умолчанию
   и не обещать в README.

## Чего НЕ делать

- Не делать выбор транспорта настройкой в интерфейсе: там только флаг
  «разрешить обфусцированный», всё остальное автоматически.
- Не менять транспорт посреди живой сессии.
- Не увеличивать суммарное время ожидания при подключении.
- Не трогать логику повтора набора ADR 0050 «заодно».
- Не писать в интерфейс догадки про DPI: мы не умеем отличать блокировку от
  плохой сети, и врать об этом нельзя.

## Definition of done

- `cargo test --workspace` не хуже базового прогона; новые тесты — на
  порядок попыток, на бюджеты и на «переподключение не расширяет гранты».
- `cargo clippy --workspace --all-targets -- -D warnings` — чисто.
- `cd apps/desktop && npm run typecheck && npm test` — зелёное.
- На паре машин: три сценария — обычная сеть, сеть с блокировкой UDP,
  двойной NAT — и по каждому в отчёте: какой путь победил и за сколько.
- Панель показывает выбранный транспорт; в логе видна причина каждого
  отката.
