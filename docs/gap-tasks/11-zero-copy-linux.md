# 11 — Zero-copy захват → энкодер на Linux

**Пункт бэклога:** 33 (вторая половина). **Зависит от:** `10` — только в
одном: тип кадра, умеющий нести GPU-дескриптор, вводится там. Если `10` ещё
не влита, вводи его здесь, а `10` потом переиспользует.
**Нужно:** Linux-машина с VA-API (Intel/AMD), сессия Wayland с работающим
порталом и PipeWire, вторая машина как гость.

## Что уже есть (проверено по коду)

- `crates/media/src/capture/pipewire_stream.rs` — потребление кадров портала
  через PipeWire (фича `capture-portal`).
- `crates/media/src/capture/linux_x11.rs` — X11-путь (`x11rb`), чисто
  программный, DMA-BUF там взять неоткуда.
- `crates/media/src/encode/linux_vaapi.rs` — VA-API H.264 (ADR 0040):
  открывает DRM-дисплей, создаёт конфиг `VAEntrypointEncSlice`, аллоцирует
  NV12-поверхности.
- `crates/media/src/capture/mod.rs` — `Frame` с `data: Vec<u8>`.
- ADR 0039: Linux-клиент везёт оба типа сессии; ни один из них нельзя
  сломать ради другого.

## Задача 1 — принимать DMA-BUF от портала

**Файл:** `crates/media/src/capture/pipewire_stream.rs`

1. Договорись с PipeWire о формате `SPA_DATA_DmaBuf` (сейчас поток
   почти наверняка забирается как `MemPtr` — проверь по коду и запиши, как
   было).
2. Отдавай наружу дескриптор (fd + modifier + stride), а не байты, через тот
   же тип кадра, что заведён пачкой `10`.
3. Компоситор может отказать в DMA-BUF — тогда путь остаётся прежним, без
   ошибки в лицо пользователю.

## Задача 2 — импорт в VA-API

**Файл:** `crates/media/src/encode/linux_vaapi.rs`

Импортируй буфер как поверхность через `VASurfaceAttribExternalBuffers` /
`vaCreateSurfaces` с memory type DRM PRIME. Устройство DRM у захвата и у
энкодера обязано быть одним и тем же — иначе это скрытая копия, ради
устранения которой всё и делается; при несовпадении честный откат.

## Задача 3 — X11 не трогаем

X11-путь остаётся программным. Не пытайся тянуть туда DRI3/Present: это
отдельный объём работы, и `capture-x11` обязан продолжать работать без
единой правки.

## Задача 4 — фича и ADR

Фича по образцу соседних (не в `default`), ADR, дополняющий 0039/0040:
какой путь активен, при каких условиях, как откатывается.

## Чего НЕ делать

- Не менять контракт трейта `ScreenCapturer`.
- Не ломать сборку без `capture-portal` и без `encode-vaapi`: `.deb` обязан
  ставиться и работать на машине без VA-API вообще (см. комментарий к фиче
  `encode-vaapi` в `crates/media/Cargo.toml`).
- Не переводить X11-путь на GPU.
- Не трогать Windows-путь (пачка `10`).
- Не «улучшать» PipeWire-аудио заодно.

## Definition of done

- `cargo clippy -p lumepeer-media --all-targets --features capture-x11,capture-portal,encode-openh264,audio-opus,audio-capture-pipewire -- -D warnings` — чисто.
- Та же команда с добавленной `encode-vaapi` и новой фичей — чисто.
- `cargo test --workspace` не хуже базового прогона.
- На Wayland-машине с VA-API: сессия идёт, картинка есть, замер CPU «до/после».
- На той же машине с принудительно выключенным DMA-BUF: сессия идёт по
  старому пути.
- На X11-сессии: ничего не изменилось.
- `.deb` на машине без VA-API по-прежнему работает на `openh264`.
