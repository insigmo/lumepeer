# 22 — Hole punching для обфусцированного пути

**Пункт бэклога:** 50. Остаток **инкремента 2** из ADR 0052.
**Зависит от:** `21`. **Нужно:** две машины за разными NAT, и хотя бы одна —
за симметричным NAT или двойным (у нас такая известна: `beta`).

## Что уже есть (проверено по коду)

- `crates/net/src/stun.rs::reflexive_addr(socket, server)` — свой STUN,
  проверен живьём. Список рефлекторов — `STUN_SERVERS` в
  `obfuscated_endpoint.rs` (Cloudflare, Google).
- `bind_host` уже держит маппинг фоновой задачей раз в
  `NAT_MAPPING_KEEPALIVE_SECS` — в ADR 0053 это прямо названо **заменой**
  синхронного одновременного пробоя, «которого одностороннему инвайту нечем
  координировать».
- Тикет везёт `obfuscated_addr` и `host_cert_fingerprint`.
- Константы уже есть: `OBFUSCATED_CONNECT_ATTEMPTS`,
  `OBFUSCATED_CONNECT_RETRY_BACKOFF_MS`.
- Известный факт из практики (важно, не игнорировать): на `beta` двойной NAT,
  и там даже relay n0 не держится. Если после этой пачки `beta` не
  пробивается — это ожидаемо, а не провал задачи.

## Задача 1 — честно назвать, что именно возможно

Односторонний инвайт не даёт канала для синхронизации «бей одновременно».
Значит настоящий одновременный пробой возможен только там, где есть **хоть
какой-то** обратный сигнал. Варианты, из которых надо выбрать и записать
выбор в ADR:

1. **Только keep-alive** (как сейчас): работает для full-cone и
   restricted-cone NAT, не работает для симметричного. Ничего не делать —
   тоже допустимый ответ, если замеры покажут, что второй вариант не
   окупается.
2. **Пробой через существующий путь iroh как сигнальный канал**: соединение
   по iroh уже поднялось, по нему передаётся «начинаем через N мс», и обе
   стороны шлют пакеты друг другу. Это не нарушает ADR 0052 (данные всё
   равно не идут через сервер, сигнал — да), но обязано быть записано в ADR
   явно, потому что меняет обещание «бессерверности».

Выбери по замеру, а не по красоте. Сначала — задача 2.

## Задача 2 — измерить, какие NAT вокруг

**Файл:** `crates/net/examples/` (расширить существующий пробник, не плодить
третий)

1. Определи тип NAT на каждой машине: сравни рефлексивный адрес, полученный
   от **разных** STUN-серверов с одного сокета. Совпали — конусный,
   различаются — симметричный.
2. Замерь, сколько живёт маппинг без трафика (это уже частично известно:
   UDP:443 с `beta` держится 120 с) и на скольких машинах адрес выживает до
   прихода гостя.
3. Числа — в отчёт. Дальнейшая работа осмысленна только там, где пробой
   реально нужен.

## Задача 3 — пробой

**Файл:** `crates/net/src/obfuscated_endpoint.rs`

1. Реализуй выбранный вариант. Одновременная отправка с обеих сторон по
   адресам из тикета, с интервалом и числом попыток **из констант** (уже
   существующих `OBFUSCATED_CONNECT_*` или новых — с обоснованием).
2. Пакеты пробоя идут тем же обфусцированным кодеком: пробой, отличимый от
   трафика, сводит на нет смысл обфускации.
3. Неудача — тихий переход на существующий путь. Пользователю показывается
   результат, а не механика.

## Чего НЕ делать

- Не тащить внешний STUN/TURN-сервер и вообще ретрансляцию данных: ADR 0052
  это запрещает.
- Не рассылать пакеты по диапазону портов «на удачу»: это выглядит как
  сканирование и ведёт себя как оно.
- Не считать пробой успешным по факту отправки: успех — это установленное
  QUIC-соединение.
- Не убирать keep-alive: он остаётся и для конусных NAT достаточен.
- Не менять формат тикета.

## Definition of done

- `cargo clippy -p lumepeer-core -p lumepeer-net --all-targets -- -D warnings` — чисто.
- `cargo test -p lumepeer-net` зелёный, включая тест на выдержку интервалов и
  числа попыток (по подставному таймеру, без сети).
- Отчёт с типами NAT обеих машин и долей успешных пробоев на серии из
  10 попыток.
- ADR с выбранным вариантом и честной формулировкой, что именно перестаёт
  быть «полностью бессерверным», если выбран вариант 2.
- Явно записано, какие конфигурации не пробиваются (симметричный ↔
  симметричный) и что для них остаётся существующий путь.
