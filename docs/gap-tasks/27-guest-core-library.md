# 27 — Гостевое ядро как переиспользуемая библиотека

**Пункты бэклога:** подготовка к 1, 2, 3 (и полезна пачке `25`).
**Зависит от:** ничего. **Нужно:** ничего — это чистый рефакторинг без
изменения поведения.

Мобильного клиента нельзя написать, пока вся логика гостя заперта внутри
Tauri-приложения. Эта пачка ничего не добавляет пользователю и обязана
ничего не сломать.

## Что уже есть (проверено по коду)

- `apps/desktop/src-tauri/src/network.rs` — **больше 8500 строк**: актор
  сессии, набор, рукопожатие, согласие, гранты, медиапоток, файлы, чат,
  адресная книга, аудит, `ActorStores`, диагностика пути
  (`path_of`, `relay_region`). Всё вперемешку с типами Tauri.
- Гостевой список возможностей собирается там же (~стр. 8200) и уезжает в
  `lumepeer_net::guest_handshake(connection, role, proof, features)`.
- `ActorStores` уже правильно устроен: пути и keystore приходят снаружи, а
  не хардкодятся — это готовый шов.
- Чисто платформонезависимые части уже вынесены: `crates/core` (сессия,
  согласие, гранты, протокол, аудит, чат), `crates/net` (эндпоинт, тикеты,
  кадрирование, файлы, keystore), `crates/media` (кодеки и захват).
- Тесты, которые обязаны остаться зелёными: `tests/integration/tests/*`.

## Задача 1 — граница

Новый крейт `crates/client` (имя обсуждаемо, но не `guest`: та же логика
нужна и служебному хосту из пачки `25`).

Что внутрь: всё, что не зависит от Tauri, — набор, рукопожатие, состояние
сессии, отправка и приём сообщений управляющего канала, приём медиапотока,
файлы, чат, история подключений, адресная книга, аудит.

Что остаётся снаружи, в `apps/desktop/src-tauri`: команды Tauri, окна,
эмиссия событий в webview, диалоги, буфер обмена ОС, автозапуск, служба.

Интерфейс крейта — **команды внутрь и события наружу**:

```rust
pub enum ClientCommand { Connect { .. }, Disconnect, SendChat { .. }, .. }
pub enum ClientEvent   { Status { .. }, ConsentRequested { .. }, Frame { .. }, .. }
```

Никаких колбэков с `AppHandle`, никакого `tauri::` в зависимостях нового
крейта. Проверяется механически: `cargo tree -p lumepeer-client | grep tauri`
должен быть пуст.

## Задача 2 — перенос без изменения поведения

1. Переноси кусками, каждый кусок — отдельный коммит, между кусками
   `cargo test --workspace` зелёный.
2. Поведение не меняется **нигде**. Ни исправлений «раз уж мы тут», ни
   переименований ради красоты, ни смены порядка сообщений. Любая
   найденная по дороге ошибка — запись в отчёт, а не правка.
3. `ActorStores` переезжает в новый крейт как есть.
4. Всё, что связано с окном (поднять окно при `ConsentRequested`, отрисовать
   кадр, показать диалог), становится событием, на которое подписывается
   десктоп.

## Задача 3 — пригодность для мобильных

1. Крейт собирается под `aarch64-linux-android` и `aarch64-apple-ios`
   **как библиотека** (это и есть критерий готовности всей пачки).
   Проверяется `cargo check --target …`; полная сборка приложения — пачки
   `28`/`29`.
2. Всё, что не собирается под мобильные цели (keystore на Secret Service,
   пути в профиле пользователя, буфер обмена ОС), уходит за `cfg` или за
   трейт с платформенной реализацией — как уже сделано с `Keystore`.
3. Никаких блокирующих вызовов файловой системы в асинхронных путях: на
   мобильных это заметно сильнее.

## Чего НЕ делать

- Не менять поведение. Ни одного «заодно исправил».
- Не тащить в новый крейт `tauri`, `arboard`, `winreg` и всё, что привязано
  к рабочему столу.
- Не переписывать актор на другую архитектуру: переносим, а не улучшаем.
- Не делить на пять крейтов «для чистоты» — один крейт, одна граница.
- Не начинать мобильное приложение в этой пачке.

## Definition of done

- `cargo test --workspace` зелёный и **тот же набор тестов**, что до
  рефакторинга (число и имена тестов не уменьшились).
- `cargo clippy --workspace --all-targets -- -D warnings` — чисто.
- `cargo tree -p lumepeer-client` не содержит `tauri`.
- `cargo check -p lumepeer-client --target aarch64-linux-android` и
  `--target aarch64-apple-ios` проходят (цели поставить через `rustup`).
- Десктопное приложение работает как раньше: ручная проверка полного
  сценария — инвайт, согласие, картинка, файл, чат, отзыв.
- В отчёте — список замеченных, но **не исправленных** дефектов.
