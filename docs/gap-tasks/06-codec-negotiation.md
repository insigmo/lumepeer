# 06 — Согласование видеокодека на проводе

**Пункты бэклога:** фундамент для 30 (H.265), 31 (AV1), 32 (VP9/VP8).
**Зависит от:** ничего. **Нужно:** ничего (всё проверяется локально).

Без этой пачки любой второй кодек невозможен: сегодня кодек нигде не
согласуется, гость просто **угадывает** его из байтов потока.

## Что уже есть (проверено по коду)

- `crates/media/src/encode/mod.rs`: `VideoCodec { H264, Av1 }`,
  `EncoderConfig::default()` → `H264`, `probe_hardware` отказывает всему,
  кроме H.264, `select_encoder` берёт аппаратный или `openh264`.
- `apps/desktop/src/view-decoder.ts`: `avcCodecString(...)` **выводит строку
  `avc1.PPCCLL` из самого Annex-B потока** (~стр. 135), а `decoderSupported()`
  (~стр. 198) спрашивает `VideoDecoder.isConfigSupported({ codec:
  'avc1.42E01E' })` — то есть проверяется ровно H.264 и ничего больше.
- IPC-контракт кадров: `CHUNK_RESPONSE_HEADER_BYTES = 8`,
  `CHUNK_FRAME_HEADER_BYTES = 13`, флаги `CHUNK_FLAG_INPUT`,
  `CHUNK_FLAG_RECORDING`, `CHUNK_FLAG_DESYNC`. Пишет заголовок
  `apps/desktop/src-tauri/src/view.rs`, читает `view-decoder.ts`.
- Строки возможностей: `FEATURE_*` в `crates/core/src/protocol.rs`, список
  гостя собирается в `apps/desktop/src-tauri/src/network.rs` (~стр. 8200)
  и уезжает через `lumepeer_net::guest_handshake(...)`
  (`crates/net/src/connection.rs`).
- Правило роста протокола: новый `MessageKind` — **только в хвост**,
  `PROTOCOL_MINOR` +1, абзац в doc-комментарий, отправка только пиру,
  объявившему нужную `FEATURE_*`. Замороженные векторы —
  `tests/interop/golden_vectors.txt`, проверяет
  `tests/integration/tests/protocol_golden.rs`.

## Задача 1 — ADR

Опиши решение: гость перечисляет кодеки, которые **реально** умеет
декодировать; хост выбирает из пересечения со своими и объявляет выбор одним
сообщением до первого кадра; H.264 — обязательный минимум, к которому
сваливается всё. Номер ADR — по правилу из `docs/gap-tasks/README.md`.

## Задача 2 — объявление возможностей гостя

**Файлы:** `crates/core/src/protocol.rs`,
`apps/desktop/src-tauri/src/network.rs`, `apps/desktop/src/view-decoder.ts`

1. Новые константы строк возможностей — по одной на кодек:
   `FEATURE_CODEC_AV1`, `FEATURE_CODEC_H265`, `FEATURE_CODEC_VP9` (значения
   `"codec-av1"` и т. д.). H.264 своей строки **не получает**: его умеют все,
   это baseline.
2. В `view-decoder.ts` расширь `decoderSupported()` до функции, которая
   возвращает список поддерживаемых кодеков, спрашивая
   `VideoDecoder.isConfigSupported` по одному профилю на кодек. Ответ —
   от браузера, не от таблицы «мы думаем, что WebView2 умеет».
3. Список должен попасть в `features` гостя до `Hello`. Если на момент
   рукопожатия окно просмотра ещё не создано — гость объявляет только то,
   что может гарантировать **процесс**, а не окно; в таком случае пробу
   делает Rust-сторона через список фич сборки, и это фиксируется в ADR.
   Выбери один вариант и обоснуй его в комментарии; молча «как получилось» —
   нельзя.

## Задача 3 — объявление выбора хостом

**Файлы:** `crates/core/src/protocol.rs`, `apps/desktop/src-tauri/src/network.rs`

1. Новый `MessageKind::MediaCodec { codec: u8 }` **в конец** перечисления;
   `PROTOCOL_MINOR` +1 с новым абзацем в doc-комментарии по образцу
   абзацев 2…10.
2. Кодировка `codec` — маленькое перечисление в `crates/core`
   (`0 = H264`, `1 = Av1`, `2 = H265`, `3 = Vp9`), с разбором, который на
   неизвестном значении возвращает `CoreError::Malformed`, а не паникует.
3. Хост отправляет сообщение **до** первого кадра медиапотока и только
   гостю, объявившему соответствующую строку. Ничего не объявил — H.264 без
   сообщения, полная совместимость со старым гостем.
4. Выбор: пересечение «что гость умеет декодировать» × «что хост умеет
   кодировать прямо сейчас» (`probe_hardware` для аппаратных, фичи сборки для
   программных). Пустое пересечение — H.264.

## Задача 4 — кодек доезжает до декодера

**Файлы:** `apps/desktop/src-tauri/src/view.rs`, `apps/desktop/src/view-decoder.ts`,
`apps/desktop/src/view-decoder.test.ts`

1. Добавь **один байт кодека** в фиксированный заголовок ответа
   `view_next_chunk` (`CHUNK_RESPONSE_HEADER_BYTES` 8 → 9) и обнови обе
   стороны разом.
   Отдельная IPC-команда «спросить кодек» отвергнута: окно может спросить
   раньше, чем согласование завершилось, и получить неверный ответ — гонка,
   которой в заголовке кадра нет.
2. `avcCodecString` остаётся для H.264 (профиль всё равно берётся из потока);
   для остальных кодеков строка конфигурации собирается по фиксированному
   профилю из таблицы, заведённой в этой же пачке.
3. Смена кодека посреди сессии не поддерживается: если байт изменился,
   декодер пересоздаётся целиком, как при `CHUNK_FLAG_DESYNC`.
4. Тесты `view-decoder.test.ts` — на разбор нового заголовка и на выбор
   строки конфигурации по каждому байту, включая неизвестный.

## Задача 5 — векторы и совместимость

**Файлы:** `tests/interop/golden_vectors.txt`,
`tests/integration/tests/protocol_golden.rs`, `crates/core/src/protocol.rs` (тесты)

1. Допиши вектор для нового сообщения **в конец**; существующие строки не
   трогай ни одним байтом.
2. Тест «старый гость (без новых строк возможностей) получает H.264 и не
   видит нового сообщения» — обязателен.
3. Тест «неизвестный байт кодека закрывает соединение как malformed, а не
   паникует».

## Чего НЕ делать

- Не менять порядок существующих `MessageKind` и не вставлять в середину.
- Не выбирать кодек по «мы собраны с фичей» без реальной пробы: ровно этот
  дефект дал пустой экран в v0.0.14 (комментарий над матрицей в
  `.github/workflows/release.yml`).
- Не реализовывать здесь ни один новый энкодер — это пачки `07`–`09`.
- Не делать H.264 необязательным и не выкидывать `openh264`.
- Не заводить «настройку кодека» в интерфейсе: выбор автоматический.
  Диагностика (какой кодек выбран) — в панель качества соединения, и только.

## Definition of done

- `cargo test --workspace` зелёный, включая новые тесты протокола и векторов.
- `cargo clippy --workspace --all-targets -- -D warnings` — чисто.
- `cd apps/desktop && npm run typecheck && npm test` — зелёное.
- Ручная проверка на двух машинах: сессия по-прежнему идёт на H.264, в
  логе видно согласование, старый клиент (собранный до этой правки)
  соединяется с новым и получает картинку.
