# Пачка 22 — накопление опыта: обезличенный итог ремонта → staging → PR

**Репозиторий:** lumepeer (серверная часть уже есть — пачка 12 в
support_knowledge) · **Зависит от:** 12, 16 (17 — для итогов с действиями) ·
**Нужно:** локальный стек шлюза + kb-api

## Цель

После завершённой задачи AI Support пользователь **может** (отдельное
согласие на каждую отправку) отправить обезличенный итог. Обычный успех по
известному документу только увеличивает счётчик и не меняет корпус;
новое знание попадает в staging и превращается в правку корпуса только
через ревью человеком и обычный PR.

## Прочитать перед началом

- `contracts.md` § 5; `schemas/repair-outcome.schema.json` и раздел
  feedback в `docs/api.md` support_knowledge (пачка 12).
- Код пачек 16–17 (цикл, история, журнал).
- `content-workflow.md` — по нему потом пишется правка корпуса.

## Задачи

### 1. Формирование итога

Когда задача завершена (модель закончила, есть проверка результата или
явный итог «не помогло»), клиент формирует итог по схеме: ОС/релиз,
симптомы (короткие фразы), id документов и действий из журнала, итог
(`fixed_verified` — только если была проверка действием/пробой, иначе
максимум `partial`/`not_fixed`), и, если модель считает, что узнала новое
(новая причина, другая версия ОС, исправление в документе), — короткое
утверждение с пометкой «не проверено». Текст утверждения модель
формирует отдельным ходом с явной инструкцией не включать данные
устройства; затем клиентское маскирование.

### 2. Показ и согласие

Карточка в конце задачи: «Помочь улучшить базу знаний?» → **полный текст
того, что уйдёт**, в читаемом виде; «Отправить» / «Не отправлять» /
«Не спрашивать». Настройка в разделе AI Support (появляется только в этой
пачке). Отказ ни на что не влияет. Отправленное — пометка в истории.
Строки — 13 локалей.

### 3. Отправка

`POST /v1/feedback` через шлюз; ответ `contains_sensitive_data` → показать,
что отправка отклонена сервером, ничего не повторять автоматически.

### 4. Ревью (проверка петли целиком)

На локальном стеке: отправить два итога — обычный успех (в
`kb_staging.doc_outcomes` вырос счётчик, предложений нет) и итог с
утверждением (появилось предложение). Через `kb proposals show` /
`resolve` пройти принятие: правка документа по `content-workflow.md`
отдельным PR в support_knowledge (в рамках этой пачки — подготовить ветку
и показать владельцу, не вливать), `kb index` переиндексировал только этот
документ, поиск через шлюз возвращает обновлённое.

## Чего НЕ делать

- Не отправлять итог без показа полного текста и явного «Отправить».
- Не включать логи, выводы проб, пути, имена, адреса, журнал целиком.
- Не делать автоматического принятия предложений и автоматического
  повышения `verification`.
- Не создавать коммит и переиндексацию при обычном успехе.

## Definition of done

- [ ] Тесты: формирование итога (без данных устройства — канареечные
      значения в выводах проб не попадают в итог), отказ сервера,
      «не спрашивать».
- [ ] Петля задачи 4 пройдена, вывод команд и ветка правки — в отчёте.
