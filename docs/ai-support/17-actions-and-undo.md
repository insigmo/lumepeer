# Пачка 17 — действия с откатом уровня 1 и первый сквозной сценарий

**Репозиторий:** lumepeer · **Зависит от:** 16 · **Нужно:** ВМ Windows,
Linux, macOS (изменения системы проверяются **только** в ВМ); локальный
стек шлюза; ключ API для одного живого прогона

## Цель

ИИ может предложить изменение из каталога; доверенный код решает, нужно ли
подтверждение, показывает человеку что изменится и как это отменить,
сохраняет состояние «до», выполняет, проверяет результат и даёт реально
откатить. Первый сквозной сценарий проверяет и исправление, и откат.

## Прочитать перед началом

- `contracts.md` § 2.1, § 2.3, § 2.4 — классы, политика, список действий.
- Код пачек 14 и 16: каталог, `decide`, исполнитель, цикл, панель.
- `crates/runtime/src/audit_store.rs` — образец хранилища и записи событий
  аудита; журнал изменений AI Support — отдельное хранилище, но факт
  «ИИ изменил X» дополнительно пишется в существующий аудит, если его
  словарь событий это допускает (иначе — расширить словарь по правилам
  аудита, без свободного текста).
- `Management.md`, разделы 8–11 — как фон по требованиям к откату.

## Задачи

### 1. Действия в каталоге

Все действия `contracts.md` § 2.3 — спецификация + реализация на
поддерживаемых ОС. Каждое действие реализует: `capture_before` →
`apply` → `verify` и, если `undo` не `irreversible`/`not_needed`,
`undo` → `verify_undo`. Результат действия — **наблюдаемое состояние
после**, а не код выхода.

- `exact` значит точно: старый список DNS (или «автоматически»), тип
  запуска и состояние службы, флаг автозапуска тем же механизмом, что и
  системный UI (Windows — `StartupApproved`), строка hosts целиком
  (резервная копия файла с правами и владельцем).
- `disk.clean_temp`, `print.clear_queue`: файлы **переносятся** в зону
  удержания на том же томе (переименование, без копирования), с исходными
  путями и метаданными; окончательное удаление — по сроку удержания
  (константа) отдельной процедурой, видимой пользователю. Не хватает
  места/другой том → действие недоступно, а не «удалим навсегда».
- `dangerous` с `undo: checkpoint` (`net.winsock_reset`, `pkg.repair`,
  `pkg.install_os_updates`) в этой пачке **отказываются** с объяснением
  «нужна контрольная точка — будет в пачке 18». В каталог их можно внести
  только вместе с реализацией 18; до неё — не вносить.
- Права: Windows — клиент уже повышен (ADR 0057). Linux — действия с
  root через `pkexec` (системный диалог polkit, Lumepeer пароль не видит),
  аргументы списком; нет `pkexec` → действие недоступно в матрице. macOS —
  действия, требующие root, в v1 недоступны (без `osascript … with
  administrator privileges`: это строка shell); честно указать в
  матрице.

### 2. Журнал изменений

Отдельное SQLite-хранилище (путь — новое поле `ActorStores`), **не**
связанное каскадом с историей переписки: удаление переписки не удаляет
данные отката незавершённой задачи (предупредить и спросить).

- Задача = разговор AI Support. Запись = одно действие: id, задача,
  инструмент, параметры (замаскированные), состояние, ссылка на
  сохранённое «до», результат проверки, время.
- Состояния: `planned` → `before_captured` → `executing` → `done` |
  `failed` | `unknown`; откат: `undo_running` → `undone` | `undo_partial` |
  `undo_failed`. Каждый переход записывается **до** следующего шага
  (запись на диск, затем действие).
- Резервные копии — в каталоге данных приложения, права только у
  пользователя/администраторов (Windows ACL, Unix 0700), с хешем;
  повреждённая копия → откат недоступен с причиной.
- Восстановление после сбоя: при старте записи в `executing`/`undo_running`
  становятся `unknown`; выполняется только `verify` (не повтор!) и
  пользователь видит фактическое состояние и доступные шаги.

### 3. Подтверждение и выполнение

- `decide` (пачка 14) решает; UI только показывает. Карточка
  подтверждения: действие человеческим языком, устройство («этот
  компьютер»), что изменится, способ отмены и его ограничения, нужна ли
  перезагрузка. Не просто «Продолжить».
- Отклонение → `tool_result` «declined by user». Отзыв разрешения
  «Изменения» между предложением и подтверждением → отказ на этапе
  выполнения (проверка в момент выполнения, не только в UI).
- Тайм-аут выполнения → `unknown` → `verify`; автоматического повтора
  изменяющей операции нет никогда.
- После ошибки проверки: остановить следующие действия хода, показать,
  что фактически изменилось, предложить откат.

### 4. UI отката

В панели — список изменений задачи (из журнала) и действия, **только когда
механизм реально есть**: «Отменить последнее изменение», «Откатить
изменения задачи» (в обратном порядке, остановка на первой ошибке,
частичный итог честно), «Показать ограничения восстановления». Откат —
тоже с подтверждением. Новые состояния панели: ожидает подтверждения,
выполняет действие, проверяет результат, восстанавливает, восстановление
завершено / частично / невозможно. Разрешение «Изменения системы»
появляется в настройках.

### 5. Сквозной сценарий

1. **Детерминированный** (в CI и на ВМ трёх ОС): двойник шлюза отдаёт
   записанную последовательность ходов модели: пробы → действие
   `net.set_dns_servers` (исправление «неверный DNS») → проверка → откат →
   проверка, что вернулось исходное. Плюс вариант с отказом
   пользователя и вариант с убитым процессом посреди действия
   (→ `unknown` → проверка после перезапуска).
2. **Живой** (одна ВМ Windows, настоящая модель): в ВМ скриптом
   прописать неработающий DNS, спросить «не открываются сайты»; ожидается:
   диагностика, ссылка на `windows.network.dns-resolution`, предложение
   действия, подтверждение, проверка; затем «Отменить последнее изменение»
   и проверка. Запись хода (без секретов), скриншоты, `usage` — в отчёт.

## Чего НЕ делать

- Не делать контрольные точки ОС, карантин, восстановление системы — 18.
- Не добавлять действие без `verify` и без честного `undo`.
- Не удалять файлы (кроме окончательной очистки зоны удержания по сроку).
- Не повторять изменяющее действие автоматически ни при каких ошибках.
- Не проверять изменения на основной машине владельца.
- Не добавлять действия сверх `contracts.md` § 2.3; новые — предложением
  в отчёте.

- [ ] Тест восстановления после убитого процесса; тест «повреждённая
      резервная копия → откат недоступен».
- [ ] Детерминированный сценарий зелёный на трёх ОС; живой — в отчёте.
- [ ] Удаление истории переписки при незавершённой задаче предупреждает и
      не удаляет журнал.
- [ ] `contracts.md` § 2.3 соответствует реализации (классы, ОС).
