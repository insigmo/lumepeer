**Репозиторий:** support_knowledge · **Зависит от:** — · **Нужно:** доступ в веб

## Цель

До первого документа базы знаний определить: какие ОС и сценарии важнее,
откуда брать знания и на каких условиях, какие данные AI Support вправе
собирать, и что именно будет наполняться в пачках 03–10. Это фундамент:
пачки контента читают результаты 01 и не пересматривают их.

## Прочитать перед началом

- `docs/ai-support/README.md` и `contracts.md` в lumepeer.
- `База знаний фиксов.md` (путь в README) — разделы 3, 4, 12, 14.4 как фон.
- `docs/platform-support.md` в lumepeer — на каких ОС Lumepeer реально
  работает: покрытие базы не должно обещать больше, чем приложение.

## Задачи

### 1. `research/os-and-distro-popularity.md`

Собрать актуальные данные (проверить, нет ли выпусков свежее указанных):
StatCounter desktop OS (мир + отдельно Россия/СНГ — у владельца русскоязычная
аудитория), Steam Hardware & Software Survey, Stack Overflow Developer Survey
(2025 или новее), DistroWatch, W3Techs (только как серверный сигнал).

Для каждого источника: дата, методология, аудитория, что именно измеряется,
ограничения. Отдельные таблицы — не один «общий рейтинг»: настольная доля,
игровая аудитория, разработчики, серверы. DistroWatch — это просмотры
страниц, не установки; так и написать.

Итог раздела: **приоритетная матрица** — ОС/версии/дистрибутивы в три
уровня (P1 — глубокое покрытие, P2 — общие документы семейства + отличия,
P3 — только реестр пробелов). Стартовый перечень из промпта — гипотеза, не
обязательство. Для Windows и macOS — статус поддержки каждой версии
(Windows 10 вне основной поддержки с 14.10.2025 — проверить и указать
ESU), для дистрибутивов — поддерживаемые релизы и EOL.

### 2. `research/source-selection.md` и `research/sources.md`

Критерии отбора и исключения, порядок авторитетности (официальная
документация вендора → репозитории и трекеры проектов → модерируемые
сообщества → статьи). Для каждого крупного источника — **проверенные**
условия использования и лицензия текста:

- Microsoft Learn, документация Apple, Ubuntu/Debian/Fedora/Arch/openSUSE
  wiki и docs, man-страницы, Stack Exchange (CC BY-SA), Arch Wiki (GFDL),
  Red Hat docs и т. д.
- Для каждого — как можно получать (ручное чтение, API, git-репозиторий
  документации), robots/ToS, ограничения частоты.

Правило, которое этот документ закрепляет для всех следующих пачек:
**текст источников не копируется**, инструкции пишутся заново своими
словами, команды и коды ошибок — факты и приводятся, источник — ссылкой.
Неизвестная лицензия не разрешает копирование.

### 3. `sources/catalog.yaml`

Машиночитаемый реестр. Поля на запись: `id`, `name`, `url`, `platforms`,
`topics`, `type` (`official`, `vendor-repo`, `community`, `article`,
`advisory`), `authority` (1–4), `license` (как указано у источника или
`unknown`), `access` (`manual`, `api`, `git`, `feed`), `checked_at`,
`limitations`, `update_policy`. Только реально проверенные источники,
без выдуманных URL. Схему для файла кладёт пачка 02 — здесь формат
описать в шапке файла комментарием.

Отдельный блок `security_feeds`: CISA KEV, MSRC Security Update Guide API
(CVRF), Windows release health, Apple security releases, SOFA
(macadmins), endoflife.date, OSV, Debian Security Tracker, Ubuntu USN/OVAL,
Arch security tracker, Red Hat/Alma/Rocky errata, NVD API. Для каждого:
актуальный адрес, формат, лицензия/условия, нужен ли ключ, лимиты. Брать в
v1 будут только те, что выбраны в задаче 4.

### 4. `research/security-assessment.md`

Объём базовой проверки безопасности v1 — ровно список из `contracts.md`
§ 3 (не расширять). Для каждой проверки: на какой ОС, какой сигнал читается,
нужны ли права администратора, какие данные читаются, риск ложного
срабатывания, что считается `not_checked`. Источники уязвимостей v1:
**KEV, MSRC (накопительные обновления → сборки), данные о версиях macOS,
endoflife.date, метаданные безопасности родных пакетных менеджеров** —
обосновать каждый, остальные (OSV, NVD, трекеры дистрибутивов) — «не в v1,
почему». Политика свежести: срок, после которого feed считается `stale`.

Явно записать границы: только своё устройство, только чтение, никаких
сканирований сети, эксплойтов, подбора паролей; результат не называется
аудитом, сертификацией или pentest.

### 5. `research/diagnostic-data-policy.md`

Какие данные собираются, где обрабатываются, что покидает устройство и
куда — опираясь на `contracts.md` § 5 (уточнить, не расширять). Маскирование
до хранения/показа/отправки, сроки хранения локальной истории и журнала
изменений, удаление по запросу, отдельное согласие на отправку итога
ремонта (пачка 22), запрет сбора «на всякий случай». Отдельно: какие данные
получает Anthropic как провайдер модели — **только факты из опубликованных
условий Anthropic со ссылками**, без придуманных сроков хранения и гарантий;
что нужно проверить владельцу.

### 6. `coverage/plan.md` и `coverage/gaps.md`

План наполнения для пачек 03–10: по приоритетной матрице — какие темы, на
каких ОС/семействах, сколько примерно документов, какой источник основной.
Сверять с перечнями тем в файлах пачек 03–10 в lumepeer и, если матрица
показывает другое, — записать расхождение в `plan.md` (пачки контента
читают его). `gaps.md` — реестр пробелов (тема, ОС, почему пусто).

### 7. README репозитория

Короткий `README.md`: назначение, структура каталогов (только созданные),
правило «Markdown в Git — единственный источник, индекс производный»,
ссылка на план в lumepeer (`docs/ai-support/`). `LICENSE` — проприетарный
текст «All rights reserved» с владельцем `beta <qwantone@gmail.com>`;
если владелец хочет открытую лицензию — спросить, не выбирать самому.

## Чего НЕ делать

- Не писать документы базы знаний (это 03–10) и не создавать
  `knowledge/`, `schemas/`, `scripts/` — их создаёт 02.
- Не выдумывать цифры долей, URL, лицензии. Нет данных — так и написать.
- Не сводить разные метрики в один рейтинг.
- Не расширять список проверок безопасности и источников уязвимостей сверх
  `contracts.md` — предложения записать отдельным разделом «на потом».
- Не скачивать дампы баз уязвимостей и не коммитить их.
- Не писать код загрузчиков feed'ов — это пачка 13.
