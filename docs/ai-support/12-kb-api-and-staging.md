# Пачка 12 — kb-api, приём предложений (staging), CLI ревью

**Репозиторий:** support_knowledge · **Зависит от:** 11 · **Нужно:** Docker

## Цель

Внутренний HTTP-сервис над индексом из пачки 11: поиск, документ целиком,
документ к проверке безопасности, приём обезличенных предложений об опыте
ремонта в staging. Плюс CLI, через который человек (или агент по просьбе
владельца) разбирает предложения и превращает полезные в обычный PR в
корпус. Сервис **не** выполняет команды, не собирает данные с устройств и
не меняет корпус.

## Прочитать перед началом

- `contracts.md` § 4.2 и § 5.
- Код пачки 11: `kb search`, схема `kb`, роли БД.
- `research/diagnostic-data-policy.md` (пачка 01).

## Стек

FastAPI + uvicorn, pydantic-модели запросов/ответов, тот же пакет `kb`
(`kb serve`), тот же код поиска из пачки 11 — без копии. Модель
эмбеддингов загружается один раз при старте; в образ она попадает на этапе
сборки с **закреплённой ревизией**, во время работы сеть для неё не нужна.

## Задачи

### 1. Эндпоинты чтения

По `contracts.md` § 4.2: `GET /health`, `POST /v1/search`,
`GET /v1/documents/{id}`, `GET /v1/checks/{check_id}`. JSON-схемы запросов
и ответов — в `schemas/api/` и в OpenAPI, который FastAPI генерирует сам;
`docs/api.md` — человеческое описание с примерами и кодами ошибок.

Ограничения входа (константы с обоснованием): длина `query`, число и длина
элементов массивов, общий размер тела. Превышение — 413/422 с понятным
кодом, не обрезание молча. Неизвестные поля — 422.

Ответ поиска содержит всё из `contracts.md` § 4.2; `score` — ровно то, что
считает поиск, без «процентов уверенности».

`/health` — только `status`, `corpus_commit`, `embedding_model`,
`index_built_at`; без адресов, версий библиотек, ошибок с трассировкой.

### 2. Аутентификация и изоляция

Сервисные токены (сравнение хешей за постоянное время), скоупы `read` и
`feedback`; токены — из переменных окружения/файла секретов, не из
репозитория. В compose сервис слушает только внутреннюю сеть; наружу его
открывает лишь шлюз (пачка 15). Ограничение одновременных запросов.

### 3. Журналирование

Структурированные логи: метод, путь, статус, длительность, число
результатов, фильтры ОС. **Без текста запроса, сообщений об ошибках
пользователя и тела предложений.** Трассировки исключений — без значений
параметров.

### 4. Staging предложений: схема `kb_staging` (миграция)

- `proposals`: `id uuid`, `received_at`, `kind` (`new_knowledge`,
  `correction`, `failed_attempt`, `outcome_only`), `os`, `release`,
  `doc_ids text[]`, `payload jsonb` (по
  `schemas/repair-outcome.schema.json`), `status` (`new`, `accepted`,
  `rejected`, `merged`), `resolution`, `pr_url`, `resolved_at`.
  Индексы: `(status, received_at)`, GIN по `doc_ids`.
- `doc_outcomes`: счётчики `(doc_id, os, release, outcome)` → `count`,
  `last_at`. Обычный успешный ремонт по известному документу только
  увеличивает счётчик — корпус, Git и индекс не трогаются.
- Срок хранения: `rejected` и `outcome_only` старше константы удаляются
  командой `kb proposals purge` (по расписанию на сервере); описать в
  `docs/operations.md`.

`schemas/repair-outcome.schema.json` — минимальный обезличенный итог:
ОС/релиз/семейство, симптомы (короткие фразы), id документов и действий,
которые использовались, итог (`fixed_verified`, `not_fixed`, `partial`),
новое утверждение (текст до лимита) с пометкой «не проверено», без
свободных полей для логов. Клиентская часть — пачка 22.

### 5. `POST /v1/feedback`

Валидация по схеме → серверное маскирование (те же правила, что в линтере:
ключи, токены, e-mail, домашние пути, IP, имена хостов) → если найдено то,
что нельзя замаскировать надёжно, — отказ 422 `contains_sensitive_data`, а
не сохранение. `outcome_only` с `fixed_verified` → только `doc_outcomes`.
Повтор того же тела (хеш) за короткое окно — идемпотентный ответ без новой
строки.

### 6. CLI ревью `kb proposals`

`list`, `show <id>` (предложение + ближайшие документы корпуса через поиск
и `kb dedup --against`), `resolve <id> --status accepted|rejected
--resolution "<почему>" [--pr <url>]`, `purge`. CLI **не пишет Markdown
сам**: принятое предложение превращается в правку документа человеком или
агентом по `content-workflow.md`, обычным PR, с теми же линтером и
дубликатами. Модельный «успех ремонта» никогда сам не поднимает
`verification`.

### 7. Образ и запуск

`Dockerfile` (многоэтапный, непривилегированный пользователь, модель
внутри образа), `deploy/docker-compose.yml` — Postgres + kb-api во внутренней
сети (шлюз добавит пачка 15), `docs/operations.md`: запуск, миграции,
полная/инкрементальная индексация, обновление корпуса на сервере
(`git pull` + `kb index`), резервная копия БД (`pg_dump` схем `kb_staging`
и `vuln` — схема `kb` восстанавливается из корпуса и в бэкапе не нужна),
восстановление.

### 8. Тесты

С настоящей БД: каждый эндпоинт, неверный/отсутствующий токен, скоуп
`read` не может отправить feedback, лимиты входа, `unsupported_platform`,
предложение с секретом отклоняется и не сохраняется, `outcome_only` не
создаёт предложение, `/health` не раскрывает лишнего.

## Чего НЕ делать

- Не открывать kb-api в интернет и не делать в нём аутентификацию
  устройств — это шлюз.
- Не делать эндпоинтов переиндексации, правки корпуса, смены статуса
  документа.
- Не хранить текст запросов поиска.
- Не писать автоматического «писателя» Markdown из предложений.
- Не добавлять очереди, Celery, Redis, фоновые воркеры — `purge` и
  индексация запускаются CLI по расписанию сервера.

## Definition of done

- [ ] `docker compose up` поднимает БД и kb-api; запрос поиска из
      `docs/api.md` возвращает реальные документы корпуса.
- [ ] Тесты зелёные с настоящей БД; в отчёте — список тестов на
      безопасность.
- [ ] `docs/api.md` и `docs/operations.md` соответствуют коду (каждый
      пример выполнен).
