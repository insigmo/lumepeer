# Порядок работы для пачек контента (03–10)

Общий для всех пачек, которые пишут документы базы знаний. Пачка контента
перечисляет темы; этот файл — как писать каждый документ.

## Перед документом

1. Найти существующее: `uv run kb dedup --against <черновик или тема>`,
   поиск по `error_signatures` и заголовкам. Выбрать и записать одно из:
   использовать как есть / дополнить существующий / дополнение `variant`
   с `extends` (только при реально других командах, пакетном менеджере,
   конфигурации, загрузке) / новый документ / отказаться (ничего не
   добавляет).
2. Свериться с `coverage/plan.md` (пачка 01): тема в P1/P2? Если тема из
   списка пачки оказалась P3 по матрице — не писать, внести в
   `coverage/gaps.md` с причиной.

## Источники

- Сначала официальная документация вендора/проекта для этой версии ОС.
  Сообщества и статьи — только чтобы дополнить (частые причины,
  подводные камни), и только из `sources/catalog.yaml`. Нужного источника
  нет в каталоге — сначала добавить его туда с проверенными условиями.
- Текст **не копируется**. Своими словами, по-английски. Команды, пути,
  коды и тексты ошибок — факты, их приводить дословно.
- `sources[].retrieved_at` — дата, когда страница реально прочитана.

## Как писать

- Тип документа по `templates/`. Общие решения — на уровне ОС или
  семейства; отличия дистрибутива — отдельным `variant`.
- Каждая команда: какие права нужны, что ожидается на выходе, что она
  меняет, как это отменить. Необратимые шаги — явно помечены и стоят после
  безопасных альтернатив.
- `Causes`: подтверждённые причины отдельно от гипотез.
- `Diagnosis` ссылается на пробы из каталога (`probe_ids`), если проба
  даёт нужный сигнал; `Fix` — на действия (`action_ids`), если шаг ровно
  совпадает с действием каталога. Остальные шаги — ручные, для человека.
  Не придумывать новые id: нужного действия нет — записать в отчёт
  пачки предложение для каталога (решает пачка 17).
- `error_signatures` — дословно, как их видит пользователь.
- Не советовать: отключать антивирус/файрвол/SIP/Secure Boot «для проверки»,
  «чистильщики реестра», `chmod -R 777`, `rm -rf` по шаблону, скачивание
  драйверов и «фиксов» с неофициальных сайтов, переустановку ОС как первый
  шаг. Если такой совет популярен — это повод для `anti_pattern` (пачка 10).

## Уровень подтверждения

- `verified` — шаги реально выполнены и результат проверен на указанных
  `versions` (в ВМ), **или** это официальная процедура вендора для этой
  версии, описанная им же.
- `partially_verified` — подтверждено официальным источником, но для другой
  версии, или выполнено только частично.
- `unverified` — только сообщества/статьи. Такие документы допустимы, но
  поиск ранжирует их ниже, а модель видит статус.

## После документа

- `uv run kb lint` и `uv run kb dedup --ci` зелёные.
- Обновить `coverage/plan.md` (сделано) и `coverage/gaps.md` (что не удалось
  и почему).
- В описании PR — таблица: `id`, решение (новый/дополнен/variant),
  основной источник, уровень подтверждения, на чём проверено.

## Объём

20–30 содержательных документов на пачку — ориентир, не план. Глубина
частых проблем важнее формального охвата. Закончились надёжные источники —
закончилась пачка; остальное — в реестр пробелов.

## Если есть ВМ

Проверка 3–5 самых частых плейбуков пачки в ВМ подходящей ОС поднимает их до
`verified` и ловит ошибки в командах. Только в ВМ, никогда на основной
машине владельца.
