# Пачка 19 — базовая проверка безопасности

**Репозиторий:** lumepeer · **Зависит от:** 14, 16; 13 — для baseline (без
неё проверки обновлений дают `unknown`) · **Нужно:** ВМ Windows, Linux
(Ubuntu + Fedora или Arch), macOS

## Цель

Локальный детерминированный движок проверок из `contracts.md` § 3: читает
состояние устройства, сравнивает с эталоном, выдаёт находки по схеме с
раздельными статусом, серьёзностью и уверенностью. Работает **без LLM и
без согласия на отправку данных провайдеру модели** — это бесплатная
часть. ИИ, если включён, только объясняет находки и предлагает
исправления из каталога.

## Прочитать перед началом

- `contracts.md` § 3 целиком, § 5.
- Документы базы `security_check` (пачки 05, 08, 09) — для каждой проверки
  там описан сигнал и интерпретация; движок реализует ровно это. Где код
  и документ расходятся — исправить документ отдельным PR в
  support_knowledge (не молча в коде).
- `research/security-assessment.md`.
- Код пачек 14, 16, 17.

## Задачи

### 1. Тип находки

`Finding` в `crates/core` (зеркало `schemas/security-finding.schema.json`):
`check_id`, `status`, `severity`, `confidence`, `remediation_available`,
`evidence[]`, `limitations[]`, `sources[]`, `data_as_of`, `checked_at`,
`needs_elevation`, `reason`. Нельзя построить находку `confirmed` без
`evidence` (конструктор, а не дисциплина).

### 2. Движок

В `crates/support`: на каждый check id — функция, использующая пробы и
прямое чтение (без повторной реализации того, что уже есть в пробах).
Правила:

- Нет данных/прав → `not_checked` с причиной; источник `stale` или
  недоступен → `unknown`; сборка новее эталона → `unknown` («данные
  отстают»), не «всё хорошо».
- Пароли и их значения не читаются никогда (`autologon` — только наличие
  настройки).
- `*.update.*`: Windows — `CurrentBuild`+`UBR` → `/v1/security/baseline`
  через шлюз (отправляется только ОС/ветка/архитектура/сборка); macOS —
  версия → baseline; Linux — родной пакетный менеджер локально (команды
  из документа пачки 08), CVE из его метаданных (если он их даёт)
  сопоставляются **локально** со списком `/v1/security/kev`.
- `win.apps.outdated` — `winget upgrade` (если `winget` есть), находка
  `potential`, не `confirmed`.
- Общая длительность и нагрузка ограничены (константы); «медленные»
  сигналы (`softwareupdate --list`, поиск обновлений Windows Update API)
  — с тайм-аутом и честным `unknown` при его превышении.
- Отчёт: охват (что проверено / не проверено и почему) + находки.
  Отчёт хранится локально (срок — константа), на сервер не уходит.

### 3. Проба и исправления в каталоге

- `security.basic_check` в каталог (`read`): модель может запустить
  проверку и получить находки (без `evidence`, содержащих пути
  пользователя).
- Исправления, у которых есть точный откат: `sec.firewall_enable`
  (Windows-профили / ufw или firewalld по документу), `sec.smb1_disable`
  (Windows, нужна перезагрузка, `undo` — включение обратно),
  `sec.guest_disable` (Windows). Каждое — по правилам пачки 17
  (`capture → apply → verify → undo`). Защитник с Tamper Protection —
  не пытаться менять программно, объяснить пользователю.

### 4. UI

Раздел «Проверка безопасности» в панели AI Support: доступен при
выключенном ИИ (работает локально; при первом запуске — короткое
пояснение, что уходит на сервер только версия ОС для сравнения, и
возможность запретить это — тогда проверки обновлений `not_checked`).
Отчёт: сначала то, что требует внимания, затем охват. Для каждой находки:
простое объяснение, серьёзность и уверенность — **отдельно**, источник и
дата данных, «Исправить» — только если в каталоге есть действие, «Спросить
ИИ» — если ИИ включён (в разговор уходит находка без лишних деталей).
Формулировки: никогда «уязвимостей нет» — «проблем по N проверкам не
найдено, не проверено: M».

Все строки — 13 локалей.

### 5. Тесты

По `База знаний фиксов.md` § 14.7 в той части, что относится к
устройству: неполные данные → `unknown`/`not_checked`; частичное
совпадение версии не `confirmed`; сбой baseline не даёт «безопасно»;
отключённая отправка версии ОС оставляет локальные проверки работающими;
в находках и отчёте нет секретов и персональных путей; проверка не
запускает расширенный аудит и не сканирует сеть. На ВМ трёх ОС — прогон
движка: таблица «проверка × ОС → статус», с ручной сверкой 3–4 находок с
реальным состоянием ВМ (например, выключить файрвол в ВМ → находка
`confirmed`, включить действием → `not_affected`, откатить).

## Чего НЕ делать

- Не расширять список проверок сверх `contracts.md` § 3.
- Не делать сетевое сканирование, проверку других устройств, «аудит
  паролей», анализ трафика.
- Не отправлять отчёт, находки или инвентарь на сервер.
- Не прятать бесплатную проверку за включением ИИ или оплатой.
- Не писать «система защищена», «уязвимостей нет», «аудит пройден».
