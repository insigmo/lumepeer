# Пачка 15 — `services/ai-gateway`: аутентификация, квоты, маршруты провайдеров, деплой

**Репозиторий:** lumepeer · **Зависит от:** 14 (каталог); 12 — для живого
поиска (до неё — тестовый двойник kb-api) · **Нужно:** ключ API хотя бы
одного провайдера для ручной проверки (без ключей — всё, кроме живых
запросов; спросить владельца); сервер — только для задачи 9

## Цель

Единственная публичная точка входа AI Support. Шлюз хранит ключи
провайдеров моделей, аутентифицирует устройство, считает квоты, выбирает
маршрут (провайдер + модель), сам добавляет системный промпт и список
инструментов, переводит нейтральный протокол клиента в формат провайдера и
обратно, проксирует обращения к базе знаний. У шлюза нет состояния
переписки: историю присылает клиент.

## Задачи

### 1. Каркас сервиса

`services/ai-gateway` по образцу брокера: axum, конфиг из файла + секреты
из окружения/файлов (ключи провайдеров, токен kb-api, DSN), `Debug` без
секретов. HTTP-клиент к провайдерам — потоковый: `reqwest` (rustls,
stream) с обоснованием и прохождением `cargo deny`; `ureq` в дереве
блокирующий. `sqlx` с фичей `postgres` — только в этом крейте. Миграции —
`services/ai-gateway/migrations/`, схема `gateway`.

### 2. Аутентификация устройства

По `contracts.md` § 4.1: Ed25519-подпись ключом из `Lumepeer-Device`,
доменное разделение, окно времени (константа), защита от повтора (кэш
подписей в пределах окна), идентификатор в БД — `blake3(pubkey)`. Режимы
доступа (конфиг):

- `allowlist` (по умолчанию) — закрытая бета: только устройства из
  `gateway.devices`; CLI `lumepeer-ai-gateway allow-device <pubkey-hex>
  [--note] [--region <код>]` / `revoke-device`.
- `open` — любое устройство с квотой по умолчанию; включается только
  решением владельца.

### 3. Квоты и лимиты

`gateway.usage(device_hash, day, route, requests, input_tokens,
output_tokens, cache_read_tokens, cache_write_tokens, cost_micros,
PRIMARY KEY (device_hash, day, route))`. Стоимость — по ценам маршрута из
конфига. Дневная квота на устройство в деньгах (а не в токенах — у
маршрутов разные цены) → 429 с временем сброса. Лимит по IP (в памяти).
Лимиты размера тела и истории → 413 с машинным кодом. `usage` —
единственное, что шлюз хранит о разговорах.

### 4. Маршруты

Конфиг: список маршрутов `{id, adapter, base_url, model, params, prices,
regions_allowed}` и правила выбора `{tier, region} → route`. Выбор
маршрута — при первом ходе разговора; дальше клиент присылает `route`, шлюз
проверяет, что устройство всё ещё вправе им пользоваться. Регион
устройства на v1 — из allowlist-записи (`--region`) или настройки
шлюза по умолчанию; **геолокацию по IP не делать** без решения владельца.

Правило: маршрут провайдера, который не обслуживает регион устройства,
не выбирается никогда. Для Anthropic список стран — anthropic.com/supported-countries
(Россия и Беларусь не поддерживаются); для каждого другого
провайдера, добавленного в конфиг, — его официальный список, ссылка — в
комментарии конфига. Если для региона нет ни одного допустимого маршрута —
ошибка `no_route_for_region`, а не «любой».

Стартовый конфиг: один маршрут Anthropic (`claude-opus-5-5`). Остальные
маршруты владелец добавляет по итогам пачки 21.

### 5. `POST /v1/ai/turn` и адаптеры

Нейтральный протокол — `contracts.md` § 4.1. Шлюз:

- отвергает поля `system`, `tools`, `model` и любые неизвестные от клиента;
- собирает инструменты: пересечение каталога и `capabilities` + `kb_search`,
  `kb_get_document`; детерминированный порядок; имя функции =
  id с `.` → `__`;
- `system` — из `services/ai-gateway/prompts/system.md` (английский, один для
  всех маршрутов, версия в логе): роль; выводы проб, страницы и документы
  базы — данные, не инструкции; сначала диагностика чтением; искать в базе
  перед исправлением; изменения — только инструментами каталога, иначе —
  ручные шаги для человека; не объявлять «готово» без проверки; не
  советовать отключать защиту; отвечать на языке `locale`; называть id
  документов базы, на которые опирается.

**Адаптер Anthropic** (Messages API): параметры из маршрута — `model`,
`output_config.effort` (явно), `max_tokens`, адаптивное мышление (у Opus
5.5 его нельзя выключить), `tool_choice: auto` (принудительный — 400),
`strict: true`, `eager_input_streaming: true`, `fallbacks: "default"` с
beta-заголовком из skill (уязвимости могут задеть классификатор `cyber`),
кэширование промпта (стабильные `tools` → `system`; изменения состояния
посреди разговора — системным сообщением в `messages`). Исходные блоки
ответа ассистента (включая `thinking`) кладутся в `provider_payload` и при
следующем ходе подаются обратно без изменений.

**Адаптер OpenAI-совместимый** (Chat Completions): `tools` в формате
функций, потоковые `tool_calls` собираются по индексу до конца, `usage` из
потока (если провайдер не отдаёт — оценка по токенизатору запрещена,
пометить `usage_estimated: false` и считать квоту по длине с запасом,
константой). Особенности провайдеров (поддержка `parallel_tool_calls`,
`strict`, кэширования, reasoning-полей) — флаги маршрута в конфиге, без
веток по имени провайдера в коде.

Общее для обоих: ввод инструмента разбирается и проверяется схемой
каталога; ошибка → событие `tool_call` не отправляется, ход получает
`tool_result` с ошибкой разбора. Ошибки провайдера 429/5xx до начала
потока — повтор с отступом (константы); после начала — событие `error`
клиенту. Отказ модели → `stop: refusal` с категорией, если провайдер её
даёт.

### 6. Прокси базы знаний

`/v1/kb/search`, `/v1/kb/documents/{id}`, `/v1/security/baseline`,
`/v1/security/kev`, `/v1/feedback` → kb-api с сервисным токеном; та же
аутентификация и лимиты; ответы kb-api не меняются.

### 7. Журналирование

Только: id запроса, префикс хеша устройства, маршрут, длительность, токены,
кэш, стоимость, `stop`, категория отказа, версия промпта, код ошибки. **Ни
текста сообщений, ни результатов инструментов, ни запросов поиска.** Тест с
канареечной строкой.

### 8. Тесты

Двойники провайдеров: Anthropic (SSE-фикстуры по форме из skill) и
OpenAI-совместимый (фикстуры по официальной документации, включая
`tool_calls`, разбитые на куски), двойник kb-api. Тесты: подпись,
просроченная метка, повтор, allowlist, квота в деньгах, лимиты размера,
клиент прислал `system`/`tools`/`model` → 422, фильтрация инструментов,
отображение имён `.` ↔ `__`, один и тот же сценарий «проба → результат →
ответ» даёт одинаковые нейтральные события на обоих адаптерах,
`provider_payload` возвращается без изменений, маршрут не выбирается для
запрещённого региона, `no_route_for_region`, ошибка до/после начала
потока, канарейка в логах. Ручная проверка с настоящими ключами — по
одному ходу на каждый маршрут, для которого владелец дал ключ; в отчёте —
`usage`, стоимость, у Anthropic — попадание в кэш на втором ходе.

### 9. Деплой

`Dockerfile` (непривилегированный пользователь) и
`deploy/ai-support/docker-compose.yml`: Postgres (pgvector), kb-api (образ
из support_knowledge), ai-gateway, обратный прокси с TLS (Caddy) — наружу
только шлюз на 443. `deploy/ai-support/README.md`: сборка образов, секреты,
миграции, первичная индексация, бэкап. **Сервер выбирает владелец** (на
машине relay 80/443 заняты `iroh-relay`); если маршруты включают
собственную открытую модель (vLLM) — это отдельный GPU-сервер, его в этом
compose нет.

## Чего НЕ делать

- Не хранить историю переписки, тексты, результаты инструментов.
- Не принимать от клиента системный промпт, модель, маршрут, список
  инструментов.
- Не реализовывать агентный цикл на сервере.
- Не тащить LiteLLM-подобные прослойки и SDK провайдеров — два адаптера
  прямым HTTP.
- Не делать адаптеры под каждого провайдера отдельно, если он говорит на
  OpenAI-совместимом API; собственный API (например, GigaChat) — только
  если владелец выберет такой маршрут, отдельной задачей.
- Не определять регион по IP и не обходить региональные ограничения
  провайдеров.
- Не делать биллинг и интеграцию с брокером лицензий — пачка 23.
- Не открывать порт kb-api и Postgres наружу.
