# Пачка 02 — `--session-host`: хост от `LocalSystem` на рабочем столе пользователя

**Репозиторий:** lumepeer · **Зависит от:** 01 · **Нужно:** этот ПК; `beta`
для живой проверки с гостем

Прочитать до начала: ADR 0169 §1, §2, ADR 0085 §4 (роль хоста), ADR 0126,
ADR 0133, ADR 0164, `docs/research/session-host-probe.md` (пачка 01).
Код: `apps/desktop/src-tauri/src/logon_host.rs`, `apps/desktop/src-tauri/src/main.rs`
(`claim_host_role`, разбор аргументов), `crates/service/src/logon_host_launch.rs`,
`crates/service/src/system_injector_launch.rs`, `crates/service/src/client_launch.rs`,
`crates/service/src/host_role.rs`, `crates/service/src/lib.rs`
(`LOGON_HOST_ARG`, коды выхода), `crates/service/src/program_data.rs`,
`apps/desktop/src-tauri/src/placement.rs`.

## Задачи

### 1. Режим `--session-host` в десктопном бинаре

- Константа `SESSION_HOST_ARG = "--session-host"` рядом с `LOGON_HOST_ARG`.
- Новый модуль `apps/desktop/src-tauri/src/session_host.rs` по образцу
  `logon_host.rs`: без Tauri и WebView, `spawn_actor_with`, отказ стартовать
  не от `LocalSystem`. Общее с `logon_host.rs` вынести в один модуль, а не
  копировать (одна реализация «кто что может» — ADR 0085 §1).
- Хранилища — консольного пользователя: SID из `WTSQueryUserToken` →
  `program_data::user_directory(<SID>)`, тот же каталог, что сейчас
  заполняет повышенный клиент. Ключ, пароль устройства, адресная книга,
  приглашение, аудит — те же, ничего не переносится.
- Присутствие: **attended** (человек за машиной есть). Согласие в этой
  пачке — временно: входящий без пароля устройства отклоняется с понятной
  причиной; нативное окно — пачка 04.
- Ввод — в процессе (`WindowsInjector`), без похода в службу: процесс сам
  стоит там, где воркер ADR 0114. Защищённый рабочий стол — прежние операции
  пайпа службы (`SY` в списке).
- Держит роль хоста (`host_role::claim`).
- Маркер: если нет `%ProgramData%\Lumepeer\session-host-enabled`, выход
  с `SESSION_HOST_EXIT_NOT_ENABLED` (новый код рядом с
  `LOGON_HOST_EXIT_NOT_ENABLED`). Нет хранилища пользователя — выход
  `SESSION_HOST_EXIT_NO_STORE`.

### 2. Запуск и надзор в службе

- `crates/service/src/session_host_launch.rs` по образцу
  `logon_host_launch.rs`: кто-то вошёл в консоль → запустить на `Default`;
  выход/смена консоли → попросить отдать роль, дождаться, завершить.
  Перезапуск после падения с ограничением частоты; после `NOT_ENABLED` и
  `NO_STORE` — не перезапускать до смены консоли.
- Передача роли от логон-хоста при входе (ADR 0164): если запущен
  session-host, служба **не** запускает клиента — гость перезванивает и
  попадает в session-host той же личности.

### 3. Клиент рядом с session-host

Повышенный клиент при занятой роли уже работает гостем (`claim_host_role` →
`Taken`). Проверить, что его окно говорит об этом понятно («хост работает в
службе»), а не молчит. Неповышенный клиент (dev-прогон) — тоже `Taken`, не
второй хост.

## Чего не делать

- Не трогать манифест клиента и списки `SDDL` службы.
- Не рисовать никаких окон из session-host (согласие — пачка 04).
- Не переносить хранилища.

## Статус (2026-10-28)

Код — ветка `unelev/02-session-host` (worktree `../lumepeer-unelev`, вместе с
пачкой 03, не закоммичено). Юнит-тесты, `clippy`, `fmt` зелёные неповышенно;
повышенный прогон службы и все живые пункты ниже **не сделаны** — нужен UAC и
установка сборки.

Что сделано не буквально по тексту пачки:

- **Присутствие — `Unattended`, а не `Attended`.** Именно это даёт «входящий без
  пароля устройства отклоняется с понятной причиной» (`Admission::refuses` →
  `ConsentUnavailable`); при `Attended` гость ждал бы согласия, которое некому
  показать. Пачка 04 вернёт `Attended` вместе с нативным окном.
- **Ввод в процессе** — новый метод `ViewWindows::injects_as_system` (по
  умолчанию `false`), актор не ходит в `inject_desktop` службы, если `true`.
- **Общий код хостов**: `apps/desktop/src-tauri/src/system_host.rs` (десктоп) и
  `crates/service/src/host_process.rs` (запуск/остановка процесса-хоста в службе).
  Оба хоста при старте **ждут** роль до 8 с вместо мгновенного `ROLE_TAKEN`:
  логон-хост и session-host передают консоль друг другу при каждом входе и
  выходе, иначе второй уходил бы в парковку на 5 минут.
- **Парковка** после `NOT_ENABLED`/`NO_STORE`/`ROLE_TAKEN` — до смены консоли
  **или 5 минут** (как у логон-хоста), а не только до смены консоли: иначе
  маркер, записанный посреди сеанса, не действовал бы до перевхода.
- **Повышенный клиент при маркере** не берёт роль и не просит её отдать, а
  окно говорит «это устройство обслуживает служба Lumepeer»
  (`status.hostedByService`, `network_status.hosted_by_service`). Кроме того
  (сделано в пачке 03), он держит хранилища в профиле — своя гостевая
  личность, без политики, — иначе два эндпоинта с одним ключом дерутся за
  реле (ADR 0169 §3). Перенос сохранённых хостов — по-прежнему пачка 07.
- **Передача от логон-хоста** при маркере запускает клиента человека (не
  «владельца»), потому что эндпоинт session-host открывается только с
  клиентом (пачка 03).

## Definition of done

- [ ] С маркером: после входа в Windows `query process` показывает
      `lumepeer-desktop.exe` в сессии 1 не от пользователя; лог службы —
      запуск; лог session-host — эндпоинт открыт с той же личностью, что у
      клиента до этого.
- [ ] Без маркера: session-host выходит `NOT_ENABLED`, клиент хостит как
      раньше.
- [ ] Гость с `beta` по паролю устройства входит, видит экран, двигает
      мышь в `regedit`; гость `VMware` получает Ctrl+V (если ВМ есть на хосте).
- [ ] Перезагрузка с включённым логон-хостом: экран входа → вход → гость
      перезванивает в session-host, личность та же.
- [ ] Тесты: юнит-тесты кодов выхода и решения «запускать/нет»
      (`cargo test -p lumepeer-service`, **повышенный** прогон); `cargo fmt`,
      `clippy`.
