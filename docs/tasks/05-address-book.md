# 05 — Адресная книга: устройства, теги, доверие

**Зависимости:** `04` (флаг `trusted` имеет смысл только вместе с постоянным
доступом).

## Что уже есть

`crates/core/src/address_book.rs` (188 строк): `AddressEntry { label, tags,
notes, trusted }`, `AddressBook` с `upsert`, `remove`, `get`, `iter`, `len`,
`is_empty`, `is_trusted`, `to_json`, `from_json`. Ключ — base32 от `NodeId`,
чтобы формат на диске не зависел от сериализации `NodeId`.

Ссылка на модуль во всём репозитории ровно одна: `pub mod address_book;` в
`crates/core/src/lib.rs`. ADR 0022, на который ссылается заголовок модуля, в
`docs/adr/` отсутствует.

Не путать с `apps/desktop/src-tauri/src/connection_history.rs` — это
**гостевая** история «куда я подключался» (ADR 0016), она подключена и
работает. Адресная книга — **хостовая** и про доверие.

## Задача 1 — Персистентность

**Файл:** новый `apps/desktop/src-tauri/src/address_book_store.rs`

Скопировать форму `ConnectionHistory` (`connection_history.rs`, стр. 55–110) —
она уже решает ровно эти вопросы правильно:
- `open(path: Option<PathBuf>)`, где `None` в тестах и при нерезолвящемся
  каталоге данных → работа в памяти, а не отказ старта (§18);
- нечитаемый файл → `tracing::warn` и пустая книга, **не** паника;
- запись через `AddressBook::to_json`, чтение через `from_json` — не писать
  второй сериализатор.

Путь — рядом с остальными файлами конфигурации, через `config::config_dir()`.
Файл содержит только публичные ключи и пользовательские подписи; секретов там
нет по построению, и так и должно остаться.

## Задача 2 — Проводка actor и IPC

**Файлы:** `network.rs`, `commands.rs`, `main.rs`, `capabilities/main.json`

- Команды: `address_book_list`, `address_book_upsert`, `address_book_remove`,
  `address_book_set_trusted`.
- **Только из главного окна.** Гость не редактирует книгу хоста.
- В DTO наружу отдавать псевдонимизированную метку пира, как это уже делает
  `label_of` (`network.rs` ~стр. 1059), плюс поля записи. Сырой `NodeId` в
  webview не отдавать.
- `address_book_set_trusted` — операция повышения доверия. Она обязана попасть
  в аудит (`AuditEvent`, см. `01`) и **никогда** не выполняться автоматически
  по факту успешного подключения.

## Задача 3 — Связь с постоянным доступом

**Файл:** `network.rs`

`AddressBook::is_trusted(peer)` становится входом в путь из `04`: только
доверенное устройство вообще допускается к проверке пароля. Недоверенное
получает обычный диалог согласия.

Важно: доверие **не заменяет** пароль. Это сужение множества тех, кому вообще
позволено пробовать, а не пропуск. Deny-by-default: `is_trusted` возвращает
`false` для всего, чего в книге нет.

## Задача 4 — UI

**Файлы:** `apps/desktop/src/`, `i18n.ts`

- Список устройств с меткой, тегами, заметкой и переключателем доверия.
- Фильтр по тегу.
- Включение доверия требует явного подтверждения с текстом, объясняющим
  последствие, а не просто чекбокса.
- Ключи i18n в `en` и `ar`; клавиатурная навигация и `aria-label` —
  `accessibility.test.ts` и `keyboard-nav.test.ts` это проверяют.

## Задача 5 — Тесты

- Юнит: `to_json`/`from_json` round-trip, `is_trusted` на отсутствующей
  записи, `remove` несуществующего.
- Хранилище: битый JSON на диске → пустая книга и предупреждение, не паника.
- Интеграционный: недоверенное устройство при включённом постоянном доступе
  идёт по обычному пути согласия, а не по парольному.

## Проверка

```sh
cargo test --workspace && cd apps/desktop && npm run typecheck && npm test && cd -
```

## Ловушки

- Метка (`label`) — то, что ввёл человек. Не использовать её как идентификатор
  ни для чего: доверие только по `NodeId`, это прямо написано в заголовке
  модуля.
- Теги и заметки — свободный текст от пользователя. Экранировать при выводе;
  `lit-html` делает это сам, но не собирай HTML строками в обход шаблонов.
- Книга не должна попадать в аудит и логи целиком: имена устройств — это
  идентифицирующие данные хоста (§15).
