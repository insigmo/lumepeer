# 12 — macOS: аудио, мониторы, проверка на живой машине

**Зависимости:** нет. **Нужен реальный Mac** — весь код здесь непроверяем
на CI, а часть написана вслепую.

## Что уже есть

- `crates/media/src/capture/macos.rs` (1261 строка): захват через
  ScreenCaptureKit, `SCShareableContent`, `select_display` уже умеет
  разрешать `CaptureTarget::PrimaryDisplay` и `Display(n)` по списку
  `content.displays()`; TCC-разрешение поднимается первым запросом
  `SCShareableContent` в процессе.
- `MacosInjector` — инъекция через `CGEvent`, посылка на HID tap.
- `crates/media/src/decode/macos_sandbox.rs` — песочница декодера через
  `sandbox_init(3)` (ADR 0019).
- Релизная матрица собирает macOS с `capture-screencapturekit,encode-openh264`
  для x86_64 и aarch64.

## Чего нет

1. **Захвата звука.** `capture_audio.rs` в заголовке прямо пишет: «macOS — not
   implemented yet; `platform_audio_capturer` refuses loudly». При этом в
   `macos.rs` ~стр. 615 стоит `config.setCapturesAudio(false)` — то есть
   ScreenCaptureKit готов отдавать звук, его просто выключили.
2. **Воспроизведения.** `playout.rs` — только WASAPI. macOS-гость не услышит
   ни звук хоста, ни микрофон.
3. **Перечисления мониторов наружу.** `host_monitors()` в `capture/mod.rs`
   реализован только под Windows; macOS попадает в ветку «вернуть один
   фиктивный монитор с нулевыми размерами», хотя `select_display` в двух
   строках ниже уже ходит по настоящему списку.
4. **Аппаратного энкодера.** VideoToolbox — см. `13-hardware-encoders.md`.

## Задача 1 — Захват звука рабочего стола через ScreenCaptureKit

**Файлы:** `crates/media/src/capture/macos.rs`,
`crates/media/src/capture_audio.rs`, `Cargo.toml` (feature)

- Включить `setCapturesAudio(true)` и забирать аудио-семплбуферы из того же
  потока. Это предпочтительный путь: он не требует установки виртуального
  устройства вывода, как классический CoreAudio-loopback.
- Отдавать наружу тот же `PcmChunk`, что и остальные бэкенды: 48 кГц, стерео,
  s16, чанк `AUDIO_FRAME_MS`. Конвертацию делать существующей
  `to_wire_pcm` — **не** писать второй ресемплер.
- Новая feature по образцу соседних: `audio-capture-screencapturekit`, инертна
  на других платформах, `cargo build --workspace` без неё не требует SDK.
- Захват аудио не должен стартовать без активного зрителя и без гранта
  `view` — то же правило, что и для пикселей (§8.1).
- macOS запрашивает отдельное разрешение на запись звука. Отказ — это
  честный `MediaError`, видеосессия продолжается без звука (§18), а не падение.

## Задача 2 — Воспроизведение на macOS

**Файл:** `crates/media/src/playout.rs`

- Добавить CoreAudio-бэкенд с той же формой, что у WASAPI: `start` открывает
  устройство вывода по умолчанию на его собственной частоте, `push` принимает
  один чанк проводного формата и конвертирует, `stop` освобождает.
- Обратная конвертация уже написана и платформонезависима — она в этом же
  файле и всегда тестируется. Переиспользовать.
- Тишина в чанке — это настоящая тишина, а не пропуск: разрывы в часах
  отправителя не должны давать щелчки. Это уже заложено в контракте модуля.

## Задача 3 — Перечисление мониторов

**Файлы:** `crates/media/src/capture/mod.rs`, `capture/macos.rs`

- Реализовать `host_monitors()` и `host_display_count()` для macOS через
  `SCShareableContent::displays()` — тот же список, по которому уже работает
  `select_display`, чтобы индексы `CaptureTarget::Display(n)` и
  `MonitorInfo.id` совпадали. Несовпадение здесь означает «гость выбрал второй
  монитор, а показали третий».
- Отдавать реальные ширину/высоту и флаг основного дисплея.
- Соблюдать `MAX_MONITORS_PER_HOST = 8`.
- Убрать macOS из ветки «вернуть один фиктивный монитор», не трогая эту ветку
  для платформ, где она ещё нужна.

## Задача 4 — TCC: разрешения и понятный отказ

**Файлы:** `macos.rs`, UI, `i18n.ts`, `apps/desktop/src-tauri/Info.plist`
(если его нет — создать по требованиям Tauri)

- Проверить наличие строк назначения (`NSCameraUsageDescription` не нужен, а
  вот описания для записи экрана и микрофона — нужны), иначе macOS убьёт
  процесс при запросе.
- Если пользователь отказал в «Записи экрана», приложение обязано сказать
  словами, что именно надо включить и где, а не показывать пустой экран.
  Заготовки уже есть: `status.noCapture` и `view.unavailable.noCapture` в
  `i18n.ts` плюс `MediaUnavailableReason::NoCaptureBackend` (ADR 0024).
  Использовать их, а не заводить третий способ сообщить то же самое.

## Задача 5 — Проверка на живой машине и запись результата

Часть macOS-кода писалась без доступа к железу. Прогнать вручную и записать,
что реально работает:

- захват основного и второго монитора, переключение между ними;
- инъекция мыши и клавиатуры после выдачи «Универсального доступа»;
- звук хоста и микрофон гостя в обе стороны;
- декодер в песочнице `sandbox_init` не падает под нагрузкой;
- Intel и Apple Silicon, если доступны обе.

Результат — в ADR, честно, включая то, что не заработало. Не «предполагается,
что работает».

## Проверка

```sh
cargo clippy -p lumepeer-media --all-targets --features capture-screencapturekit,encode-openh264 -- -D warnings
cargo test --workspace
```

## Ловушки

- `objc2`-биндинги в `crates/media/Cargo.toml` подобраны под те версии,
  которые уже резолвит дерево `apps/desktop/src-tauri` (tauri/tao/objc2-app-kit)
  — это проверено по `Cargo.lock` и прямо описано в комментарии. Не поднимай
  мажорную версию objc2 ради удобства: получится две несовместимые
  objc2-вселенные в одном процессе.
- `SCShareableContent` — иммутабельный снимок. Передача его между очередями
  обоснована в комментарии `ContentHandoff`; при добавлении аудио не нарушай
  это рассуждение и обнови комментарий, если меняешь то, что через хэндофф едет.
- `crates/media` — единственное место с разрешённым `unsafe`, и стандарт
  обоснования задан ADR 0005. Каждый новый `unsafe`-блок объясняет, почему он
  корректен.
