# 02 — Буфер обмена end-to-end

**Зависимости:** `01` (без выдаваемых грантов проверки всегда дают `false`).

## Что уже есть

- `crates/core/src/clipboard.rs` — валидация §9.2 (только UTF-8, лимит
  `CLIPBOARD_MAX_BYTES`) и `ClipboardSync` с подавлением эхо-петли
  (`local_changed`, `remote_received`, `reset`).
- `MessageKind::ClipboardSync` в протоколе, отправка в
  `Actor::on_clipboard_push` (`network.rs` ~стр. 2353), приём в `on_inbound`
  (~стр. 1761), стейджинг в `clipboard_inbound`, уведомление
  `ActorNotification::ClipboardFromPeer`.
- IPC-команды `clipboard_push` / `clipboard_pull` (`commands.rs` ~стр. 786–822),
  разрешения в `capabilities/main.json`.

## Чего нет

1. Никто **никогда не читает и не пишет системный буфер обмена**. Ни одной
   зависимости на это в дереве нет.
2. UI не вызывает `clipboard_push`/`clipboard_pull` **ни разу** — проверь сам:
   `grep -rn clipboard_push apps/desktop/src` даёт пусто.
3. Проверки грантов на приёме перепутаны местами (см. задачу 1).

## Задача 1 — Починить перепутанные проверки грантов на приёме

**Файл:** `apps/desktop/src-tauri/src/network.rs`, `on_inbound`, ветка
`MessageKind::ClipboardSync`.

Семантика грантов (она задана §8.2 и отправляющей стороной в
`on_clipboard_push`):
- `clipboard_read` — «гость может **читать** буфер хоста», то есть хост шлёт
  свой буфер гостю;
- `clipboard_write` — «гость может **писать** в буфер хоста», то есть гость
  шлёт свой буфер хосту.

Сейчас на приёме условия зеркальны отправке: гость, принимающий буфер хоста,
проверяет `clipboard_write`, а хост, принимающий буфер гостя, проверяет
`clipboard_read`. Пока оба гранта недостижимы, это незаметно; после `01` при
включённом только одном гранте буфер молча перестанет работать.

Делать: привести приём в соответствие с отправкой, и **закрыть это тестом** в
`tests/integration/tests/consent_cycle.rs` — по одному тесту на каждое
направление, с включённым ровно одним грантом.

Не делать: не «чинить» отправку под приём. Отправка соответствует §8.2.

## Задача 2 — Доступ к системному буферу на стороне Rust

**Файлы:** `Cargo.toml` (workspace deps), `apps/desktop/src-tauri/Cargo.toml`,
новый модуль `apps/desktop/src-tauri/src/clipboard_os.rs`

- Взять `arboard`. Именно на стороне Rust, **не** через плагин Tauri с
  правом для webview: webview — недоверенный слой представления (§2.3), давать
  ему доступ к буферу хоста нельзя.
- Модуль даёт узкий трейт вида `trait OsClipboard { fn read_text(&mut self) -> Option<String>; fn write_text(&mut self, text: &str) -> Result<()>; }`
  и реализацию поверх `arboard`, плюс no-op реализацию для сборок и тестов без
  дисплея. Трейт нужен, чтобы actor тестировался без реального X-сервера —
  посмотри, как это сделано для захвата экрана (`SharedCapture`,
  `test_capture()` в тестах `network.rs`).
- Ошибка чтения буфера — это `None` и `tracing::debug`, а не паника и не
  срыв сессии. Буфер обмена может быть занят другим процессом в любой момент.
- Прогнать `cargo deny check` — новая зависимость проходит через тот же гейт,
  что и все остальные.

## Задача 3 — Наблюдатель за локальным буфером

**Файлы:** `apps/desktop/src-tauri/src/network.rs`,
`crates/core/src/constants.rs`

- Опрос с интервалом: у `arboard` нет кросс-платформенных уведомлений об
  изменении. Интервал — **новая константа** `CLIPBOARD_POLL_INTERVAL_MS` в
  `constants.rs` с doc-комментарием. Не хардкодить число в actor.
- Опрос запускается только пока есть хотя бы одна активная сессия с
  `clipboard_read` (хост) или `clipboard_write` (гость), и останавливается,
  когда таких сессий не осталось. Это тот же принцип, что «нет зрителя — нет
  захвата» (§8.1): не читать буфер пользователя без действующего гранта.
- Изменение прогоняется через `ClipboardSync::local_changed` — он уже гасит
  эхо. Не изобретать второй механизм подавления.

## Задача 4 — Применение входящего буфера и UI

**Файлы:** `network.rs`, `apps/desktop/src/session-status.ts` или
`view-window.ts`, `i18n.ts`

- Входящий `ClipboardSync` после проверки гранта пишется в системный буфер
  через `OsClipboard::write_text`, и результат помечается в `ClipboardSync`
  как применённый (иначе наблюдатель из задачи 3 отправит его обратно).
- `clipboard_pull` остаётся: он нужен UI, чтобы показать «буфер получен от
  партнёра», без вываливания содержимого в broadcast-канал (§15).
- В UI — ненавязчивый индикатор факта синхронизации. **Не показывать
  содержимое буфера в общем окне** и не писать его в лог: §15 запрещает
  содержимому буфера попадать в аудит и телеметрию.
- Ключи i18n в `en` и `ar`.

```sh
cargo test --workspace && cargo deny check && cd apps/desktop && npm test && cd -
```

## Ловушки

- `CLIPBOARD_MAX_BYTES` — 64 KiB. Большая вставка обрезается **отказом**
  (`CoreError::Malformed`), а не молчаливым усечением: усечённая вставка хуже
  отсутствующей.
- Только текст. Изображения и списки файлов вне области §9.2 для v1 —
  не расширять формат по ходу.
- `arboard` на Linux требует живого соединения с дисплеем; в CI его нет.
  Тесты обязаны идти через трейт с no-op реализацией, иначе `build`-джоба
  упадёт на headless-раннере.
