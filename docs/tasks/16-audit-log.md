# 16 — Журнал аудита: подключить хранилище

**Зависимости:** желательно после `01` (там появляется событие смены гранта).

## Что уже есть

`crates/core/src/audit.rs` (88 строк): `AuditEvent` со всеми интересными
случаями (`ConsentRequested`, `ConsentGranted`, `ConsentRevoked`,
`ConsentRejectedQueueFull`, `ConsentRejectedGuestLimit`, `InputToggled`,
`RecordingToggled`, `FileAction`, `ProtocolViolation`), `AuditRecord`
с псевдонимизированным пиром, функция `peer_hash` (BLAKE3 от
`install_salt || node_id`), трейт `AuditSink` и `NullAuditSink`.

## Чего нет

Реального sink. Проверь сам:

```sh
grep -rn "AuditSink\|AuditRecord" crates apps services --include=*.rs | grep -v "crates/core/src/audit.rs"
```

Единственное, что используется из модуля за его пределами — `peer_hash`, и то
для формирования отображаемых меток пиров в `network.rs` (~стр. 723, 742).
**Ни одно событие никуда не записывается.** Doc-комментарий у `AuditSink`
прямо называет это работой фазы 4: append-only таблица SQLite, срок хранения
30 дней, экспорт и удаление через UI (§15).

## Задача 1 — Постоянная соль установки

**Файлы:** `apps/desktop/src-tauri/src/`, `crates/net/src/keystore.rs`

`peer_hash` требует `install_salt: &[u8; 32]`. Сейчас в `network.rs` для меток
используется константа `HOST_LABEL_SALT` — для отображаемых меток этого
достаточно, для аудита нет.

- Соль генерируется один раз при первом запуске и сохраняется. Место —
  keystore (обобщённый слот появляется в `04-unattended-access.md`, задача 1;
  если та задача ещё не сделана, допустим отдельный файл рядом с конфигом, но
  с пометкой `TODO` и ссылкой на неё).
- Смена соли обесценивает весь предыдущий журнал: одинаковые пиры перестанут
  сопоставляться. Поэтому соль **не** пересоздаётся при отсутствии файла, если
  журнал непустой — это ошибка, о которой надо сказать, а не тихо начать
  заново.

## Задача 2 — Sink на SQLite

**Файл:** новый `apps/desktop/src-tauri/src/audit_store.rs`

- Таблица append-only: ни `UPDATE`, ни `DELETE` по одной строке. Удаление —
  только целиком по сроку хранения или по явной команде пользователя.
- `AuditSink::append` **не должен блокировать путь согласия** — это записано
  прямо в контракте трейта. Значит запись идёт через канал в отдельный поток,
  как это уже сделано в `apps/desktop/src-tauri/src/recorder.rs`: очередь
  ограниченной глубины, переполнение роняет запись со счётчиком, а не
  подвешивает вызывающего. **Скопируй форму оттуда.**
- Сбой открытия базы — предупреждение и работа с `NullAuditSink`, а не отказ
  старта (§18).
- `services/broker` — единственный компонент с базой данных; у хостов её нет.
  Здесь речь о локальном файле приложения, никакой сети.

## Задача 3 — Срок хранения 30 дней

**Файлы:** `audit_store.rs`, `crates/core/src/constants.rs`

- Константа `AUDIT_RETENTION_DAYS` в `constants.rs` с doc-комментарием и
  ссылкой на §15. Не хардкодить 30 в SQL.
- Чистка при запуске и раз в сутки, не при каждой записи.
- Записи старше срока удаляются безусловно, включая нарушения протокола: §15
  задаёт срок хранения, а не «хранить интересное дольше».

## Задача 4 — Записывать события

**Файл:** `apps/desktop/src-tauri/src/network.rs`

Проставить вызовы sink там, где события действительно происходят:

| Событие | Где |
|---|---|
| `ConsentRequested` / `ConsentGranted` / `ConsentRevoked` | `on_grant`, `on_revoke`, приём `ConsentRequest` |
| `ConsentRejectedQueueFull` / `ConsentRejectedGuestLimit` | там, где `SessionManager` возвращает соответствующую ошибку |
| `InputToggled` | смена роли, влияющая на грант `input` |
| `RecordingToggled` | `on_record_toggle` |
| `FileAction` | задачи из `03-file-transfer.md` |
| `ProtocolViolation` | места, где соединение закрывается по коду ошибки |

Категорически нельзя писать в журнал: сырой `NodeId`, тикеты, токены, IP,
имена файлов, содержимое буфера обмена и текст чата. Это перечислено в
заголовке модуля, и `FileAction` намеренно несёт `&'static str` тег, а не имя
файла — не «улучшай» его до `String`.

## Задача 5 — Экспорт и удаление в UI

**Файлы:** `commands.rs`, `main.rs`, `capabilities/main.json`,
`apps/desktop/src/`, `i18n.ts`

- Просмотр журнала списком с фильтром по дате и типу события.
- Экспорт в файл — нативным диалогом со стороны Rust, без права `fs` у
  webview.
- Удаление всего журнала — с подтверждением. §15 требует, чтобы пользователь
  мог и выгрузить, и стереть.
- Ключи i18n в `en` и `ar`.

## Проверка

```sh
cargo test --workspace && cd apps/desktop && npm run typecheck && npm test && cd -
```

## Ловушки

- Псевдонимизация — не украшение. Если в журнал попал сырой `NodeId`, задача
  не сделана: смысл `peer_hash` в том, что журнал можно отдать наружу, не
  раскрывая, с кем именно человек соединялся.
- Аудит — это свидетельство, а не вход авторизации. Поэтому там настенное
  время (`at_unix_secs`), и защита от перевода часов §12.3 к нему **не**
  применяется. Не переделывай это на монотонные часы.
- Не добавляй в журнал того, чего нет в `AuditEvent`, через свободный текст.
  Нужен новый случай — новый вариант enum с обсуждением того, что он несёт.
