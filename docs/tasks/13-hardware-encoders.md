# 13 — Аппаратные энкодеры: VideoToolbox и VA-API

**Зависимости:** нет.

Читать до начала: `docs/adr/0011-windows-hardware-encoder.md` и
`crates/media/src/encode/windows.rs`. Windows-путь уже сделан правильно, и эта
задача — повторение того же подхода на двух других платформах, а не
изобретение своего.

## Что уже есть

`crates/media/src/encode/mod.rs`, `probe_hardware` (~стр. 97). Его
doc-комментарий описывает и текущее состояние, и стандарт качества: на Windows
он по-настоящему перечисляет и активирует аппаратный H.264 MFT через
`MFTEnumEx` с `MFT_ENUM_FLAG_HARDWARE` и сообщает `EncoderKind::Hardware`
только если тот действительно создался и принял NV12 на вход и H.264 на выход
— «never a hopeful guess».

`VideoToolbox`, `MediaCodec` и VA-API там же названы работой фазы 4 (§19),
поэтому на всех платформах кроме Windows возвращается `None`.

`select_encoder` уже содержит ветку для не-Windows платформ, которая честно
падает с `EncoderUnavailable`, если `probe_hardware` вдруг сообщит о бэкенде,
конструктор которого не подключён. Эта ветка — страховка ровно от той ошибки,
которую легко сделать в этой задаче: **включить probe, забыв конструктор**.

## Стандарт, ниже которого работа не принимается

1. `probe_hardware` возвращает `Hardware` **только** если энкодер реально
   создался и принял NV12 на вход и H.264 на выход. Не «драйвер есть», не
   «устройство перечислилось».
2. Есть тест вида `probe_hardware_agrees_with_whether_construction_actually_works`
   (он уже написан для Windows, `encode/windows.rs` ~стр. 1051) — то есть
   проверка того, что probe не врёт. Повторить для каждой новой платформы.
3. Отказ аппаратного пути — это тихий откат на openh264 с записью в
   `tracing::info`, а не ошибка сессии.
4. Каждая новая фича инертна на чужих платформах, и `cargo build --workspace`
   по-прежнему не требует ни одного платформенного SDK.

## Задача 1 — VideoToolbox (macOS)

**Файлы:** новый `crates/media/src/encode/macos.rs`, `encode/mod.rs`,
`crates/media/Cargo.toml`

- Feature `encode-videotoolbox`, по образцу `encode-mf`: гейтит только модуль,
  зависимости объявляются в macOS-таблице целей.
- Аппаратный H.264 через `VTCompressionSession`. Формат кадра — NV12, тот же,
  что уже отдаёт `capture/macos.rs`.
- Смена целевого битрейта на лету обязана работать: `AbrController` меняет
  битрейт до `ABR_ADJUST_MAX_RATE_PER_SEC` раз в секунду, и энкодер, который
  требует пересоздания на каждое изменение, здесь бесполезен.
- Метод `request_keyframe`, если параллельно делается `07-connection-quality.md`.
- Добавить `encode-videotoolbox` в `MACOS_MEDIA_FEATURES` (`Taskfile.yml`
  стр. 22) и в macOS-строки матрицы `release.yml` — иначе получится второй
  Wayland: код есть, в продукте нет.

## Задача 2 — VA-API (Linux)

**Файлы:** новый `crates/media/src/encode/linux_vaapi.rs`, `encode/mod.rs`,
`Cargo.toml`

- Feature `encode-vaapi`.
- VA-API покрывает Intel и AMD. NVIDIA через NVENC — **отдельная задача**,
  не смешивать: другой SDK, другие лицензионные условия, другой гейт
  `cargo deny`.
- Аппаратный энкодер может отсутствовать на конкретной машине даже при
  установленных библиотеках. Это ровно тот случай, ради которого probe обязан
  реально создавать сессию.
- Не делать `encode-vaapi` обязательной для Linux-сборки: пакет должен
  ставиться и работать на машине без VA-API, откатываясь на openh264.

## Задача 3 — Согласование с AV1

**Файл:** `encode/mod.rs`

`select_encoder` отклоняет `VideoCodec::Av1` без аппаратной поддержки:
программного AV1 в v1 нет, а §11 требует **взаимной** аппаратной поддержки.
Комментарий у `probe_hardware` отдельно предупреждает, что нельзя выдавать
ответ про H.264 за ответ про AV1.

- Если новый бэкенд умеет AV1 — probe для AV1 должен проверять **AV1**, а не
  переиспользовать проверку H.264.
- Если не умеет — возвращать `None` для AV1 явно, как это уже делает
  Windows-модуль.

## Задача 4 — Замеры и тесты

- Сравнить с openh264 на одной и той же нагрузке: задержка кодирования, CPU,
  качество при равном битрейте. Результат — в ADR: аппаратный энкодер не
  всегда лучше, и решение «включать по умолчанию» должно на чём-то стоять.
- Тест «probe не врёт» из стандарта выше — обязателен.
- Тест на смену битрейта на лету.
- `cargo deny check` на новые зависимости.

## Проверка

```sh
cargo build --workspace
```

Эта команда обязана проходить без единой платформенной фичи. Затем:

```sh
cargo clippy -p lumepeer-media --all-targets --features encode-vaapi -- -D warnings
cargo test -p lumepeer-media
```

## Ловушки

- `ENCODE_HW_EVENT_TIMEOUT_MS` уже есть в `constants.rs` — использовать его
  для ожидания событий энкодера, не заводить свой таймаут.
- `ENCODE_MAX_SOFTWARE_THREADS` относится только к программному пути.
- Аппаратный энкодер, зависший на кадре, обязан отваливаться по таймауту и
  откатываться на программный, а не подвешивать цикл захвата.
