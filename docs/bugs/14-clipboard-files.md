# 14 — Файлы через буфер обмена

**Зависимости:** `10` (автоматический текстовый буфер). Пачка 9.

Решение принято, см. `DECISIONS.md`, **D5**, пункт 2. Это **фича, а не
багфикс**: новое протокольное сообщение, платформенный код в трёх местах,
новый ADR.

**Файлы:**
- `apps/desktop/src-tauri/src/clipboard_os.rs`
- `apps/desktop/src-tauri/src/network.rs`
- `crates/core/src/protocol.rs`, `crates/core/src/constants.rs`
- `crates/core/src/clipboard.rs`
- `apps/desktop/src/file-transfers.ts`, `apps/desktop/src/i18n.ts`
- `docs/adr/` — новый ADR

## Симптом со слов пользователя

«Если файл скопировали на 1 хосте, можно вставить на другом хосте»

## Что есть и чего нет

**Есть движок передачи файлов, целиком:** `file_offer` / `FileOffer` /
`FileAccept` / `FileTransferStart`, отдельный ALPN `rd/file/1`, открываемый
лениво только после принятого предложения, ограничение
`FILE_OFFER_MAX_BYTES`, хеширование, `crates/core` как точка авторизации
через грант `file_transfer` (ADR 0032).

**Нет чтения файловых списков из буфера обмена.** `clipboard_os.rs` работает
только с текстом (`String`), решением §9.2 v1. `arboard` файловых списков не
отдаёт.

Значит эта задача — **склейка**, а не новый движок: «в буфере появились пути
→ предложить их через существующий механизм → на другой стороне положить
принятые файлы и подставить их пути в буфер».

## Платформенная часть

| ОС | Формат в буфере | Как читать |
|---|---|---|
| Windows | `CF_HDROP` | `DragQueryFileW` по хендлу из `GetClipboardData` |
| X11 / Wayland | MIME `text/uri-list` | через тот же selection-механизм, что и текст |
| macOS | `NSPasteboardTypeFileURL` (совр.) / `NSFilenamesPboardType` | `NSPasteboard` |

Ни одна из трёх не покрывается `arboard`. Варианты: другая библиотека или
свой платформенный код. **Выбрать один и обосновать** — если добавляется
зависимость, она проходит через `deny.toml`, как все остальные.

Обязательна заглушка для CI: `clipboard_os.rs` уже имеет seam `OsClipboard`
ровно потому, что CI без дисплея, и `arboard` там не работает. Новый код
обязан вписаться в тот же seam, а не обойти его.

## Что сделать

### Задача 1 — Чтение списка путей из буфера

1. Расширить трейт `OsClipboard` методом, возвращающим текущий список путей,
   `Option<Vec<PathBuf>>`. `None` — «в буфере не файлы», это не ошибка.
2. Три платформенные реализации плюс заглушка для тестов.
3. Читать **на том же выделенном потоке**, что и текст. Причина в шапке
   `clipboard_os.rs` и в ADR 0027: чтение буфера — round trip к чужому
   приложению, на актор-лупе ему не место.
4. Ограничения **до** любой аллокации: максимум файлов в списке (новая
   константа в `crates/core/src/constants.rs`), максимум длины пути. Список
   из буфера — недоверенный ввод.

### Задача 2 — Протокольное сообщение

Новое сообщение: «в моём буфере лежат вот эти файлы» — имена и размеры, **не
пути**. Полный путь на чужой машине никому не нужен и является утечкой
информации о ней.

Правила добавления в протокол — `docs/tasks/03-file-transfer.md`, задача 1:
новый `FEATURE_*` бит, отправка только объявившему его пиру, валидация на
приёмной стороне, отрицательный тест в `protocol_negative.rs`.

Сообщение **не передаёт содержимое**. Оно только говорит: «есть что
вставить». Байты идут через существующий `rd/file/1` и только после согласия.

### Задача 3 — Приём: согласие человека остаётся

**Автоматически файлы на диск не пишутся.** Приём файла — решение человека,
и это не обсуждается: сейчас так работает `FileOffer`/`FileAccept`, и это
правильно.

Сценарий:

1. На принимающей стороне появляется предложение — там же, где сейчас
   появляются обычные предложения файлов (`file-transfers.ts`,
   `fileTransferPanel`), с пометкой «из буфера обмена».
2. Человек принимает. Дальше — существующий путь передачи целиком, с
   `file_transfer` грантом, лимитами и хешированием.
3. После завершения приёма файлы лежат во временном каталоге приложения, и
   **их пути подставляются в системный буфер** принимающей машины — чтобы
   «вставить» действительно сработало.
4. Временный каталог чистится при завершении сессии. Файлы, оставшиеся от
   прошлых сессий, — это утечка.

### Задача 4 — Грант

Файлы через буфер идут под грантом **`file_transfer`**, а не под
`clipboard_read`/`clipboard_write`. Это передача файлов, просто с другой
точкой входа.

Проверить: хост, выключивший `file_transfer`, но оставивший буфер обмена, не
должен получать файлы никаким путём. Это тест, а не рассуждение.

### Задача 5 — ADR

Новый ADR (следующий свободный номер). В нём:

- почему файлы из буфера — это `file_transfer`, а не расширение буфера;
- почему передаются имена и размеры, а не пути;
- почему приём остаётся решением человека;
- как это соотносится с ADR 0032 и с ADR по задаче `10`.

## Чего делать НЕ нужно

- **Не писать файлы на диск без согласия человека.** Ни при каких настройках.
- **Не передавать полные пути** с исходной машины.
- **Не обходить `FILE_OFFER_MAX_BYTES`** и остальные лимиты движка передачи.
- **Не читать буфер на актор-лупе.**
- **Не выводить содержимое файлов и полные пути** в UI, логи или журнал
  аудита.
- **Не заменять `clipboard_read`/`clipboard_write` на `file_transfer` для
  текста.** Текст остаётся под своими грантами.
- **Не обходить seam `OsClipboard`** — иначе тесты перестанут запускаться в CI.
- Не добавлять зависимость мимо `deny.toml`.

## Definition of done

- [x] Файл, скопированный на одной машине, вставляется на другой после
      явного согласия принимающей стороны.
- [x] Передаются имена и размеры, не пути.
- [x] Лимиты на количество файлов и длину пути проверяются до аллокации;
      есть отрицательные тесты.
- [x] Работает под грантом `file_transfer`; есть тест на его отсутствие.
- [x] Временный каталог чистится при завершении сессии.
- [x] Есть заглушка для CI; тесты проходят headless.
- [x] Сообщение уходит только пиру, объявившему `FEATURE_*`.
- [x] ADR написан (0047 — переномерован при слиянии, см. ниже).
- [x] Все проверки из `docs/bugs/README.md` пройдены (см. ниже — с одной
      известной оговоркой про окружение сборки, не про код).

## Что оказалось на самом деле

Агенту, выполнявшему эту задачу, было сказано, что пачка 6
(`10-clipboard-auto.md`) уже вошла в текущий `master` и что следующий
свободный номер ADR — 0046, занятый её собственным ADR
(«the-guest-side-of-clipboard-sync-goes-automatic»). Ни то, ни другое не
подтвердилось на фактической ветке, от которой был создан этот worktree:

- `apps/desktop/src-tauri/src/clipboard_os.rs` на момент начала работы
  ссылался только на ADR 0030, без единого упоминания гостевого чтения
  буфера или ADR 0046.
- `apps/desktop/src/toolbar.ts` всё ещё содержит ручную кнопку
  `sendClipboard`/`clipboardPush` (`toolbar-clipboard`, `@click=
  ${actions.sendClipboard}`) — то есть автоматической синхронизации текста
  гость→хост в этой ветке нет.
- `crates/core/src/protocol.rs` на момент начала работы был на
  `PROTOCOL_MINOR = 6` (последнее сообщение — `ReceiverReport`), без
  `StreamScaleRequest`/`FEATURE_STREAM_SCALE` пачки 5.
- В `docs/adr/` файла `0046-*.md` не было; последний существующий —
  `0045-forgetting-the-consent-rate-after-a-clean-session.md`.

(Отдельное наблюдение по ходу проверки: в этом же worktree обнаружилось, что
абсолютные пути вида `C:\Users\...\git\lumepeer\...` — то есть путь
основной, не-worktree копии репозитория — указывают на копию, которая
активно меняется параллельно этой сессией: конкурентная работа над другими
пачками, судя по всему, продолжает выполняться там, а не в изолированных
worktree. Инструменты чтения/поиска в этой сессии по ошибке дважды
обращались по такому абсолютному пути вместо пути этого worktree, что и
вскрыло факт независимо. Начиная с этого момента в сессии все операции
велись только по пути настоящего worktree
(`.claude/worktrees/agent-a75f3b582f3429b35`), и все факты из этого раздела
проверены заново именно там.)

Согласно правилу самого README («если план не работает как написано —
остановиться, сказать явно, выбрать самый консервативный вариант,
согласующийся с ground rules и D5, и продолжить, а не молча выбрать другой
путь»), решение было таким:

1. **Не блокироваться на отсутствии пачки 6.** Зависимость задачи 14 от
   задачи 10, заявленная в `docs/bugs/README.md`, оказалась зависимостью
   только по общим файлам (`clipboard_os.rs`), а не по функциональности:
   чтение файлового списка с буфера реализовано как **однократное,
   инициируемое пользователем действие** (`file_offer_clipboard` →
   `ClipboardWorker::read_files`), а не как продолжающийся фоновый опрос —
   то самое, что как раз добавляет пачка 6 для *текста*. Гостевая сторона
   вопроса «можно ли» для файлов уже решена существующим `may_transfer_files`
   (открытый вид, а не грант — тот же механизм, что ADR 0032 ввёл для
   обычного оффера), так что инфраструктура пачки 6 файлам вообще не
   требовалась. Подробное обоснование — в самом ADR 0046, раздел
   «Consequences».
2. **Использовать номер ADR, который реально свободен в этой ветке.**
   Проверено заново по правилу `docs/adr/0001`, «Numbering»:
   `grep -rho "ADR 0[0-9][0-9][0-9]" crates apps services docs --include=*.rs
   --include=*.md` + `ls docs/adr` в этом worktree. Наибольший
   процитированный и при этом существующий номер — 0045; 0046 нигде не
   процитирован и файла с этим именем нет — значит, свободен. (Отдельно
   обнаружено: `docs/adr/0035-*.md`, `e2e/ci-stand.sh` и `e2e/smoke.toml`
   ссылаются на «ADR 0036», которого не существует в `docs/adr/` — тот же
   разрыв, что задача `10-clipboard-auto.md` описывала бы для своей ветки.
   Это не моя задача чинить — см. «Найдено попутно».)
3. **Задачи 1–5 реализованы полностью**, на актуальном состоянии кода этой
   ветки (`PROTOCOL_MINOR` 6 → 7, а не 7 → 8), без предположения, что
   пачка 6 когда-либо была применена.

Итог для того, кто будет ревьюить эту работу на ветке, где пачка 6 (и,
возможно, пачка 5) уже слиты: `PROTOCOL_MINOR`/номера дискриминантов и номер
ADR, использованные здесь, были верны для состояния кода на момент работы;
при слиянии после пачек 5/6 они почти наверняка потребуют ручного
перебазирования (новый `PROTOCOL_MINOR`, новые номера дискриминантов после
`StreamScaleRequest`, возможно другой свободный номер ADR, если что-то ещё
процитировало 0046 в промежутке). Само проектное решение (файлы —
`file_transfer`, не текстовый буфер; независимость от пачки 6) от этого не
меняется.

**Подтверждено при слиянии.** Пачки 5 и 6 к этому моменту уже слиты в
`master`; 0046 занят ADR пачки 6. Ребейз сделан ровно так, как предсказано
выше: `PROTOCOL_MINOR` 7 → 8, `ClipboardFileOffer`/`ClipboardFileAccept`
переставлены на дискриминанты 39/40 (после `StreamScaleRequest`, а не после
`ReceiverReport`), ADR этой задачи переномерован в 0047
(`docs/adr/0047-clipboard-files-are-a-file-transfer-not-a-clipboard-
extension.md`). Независимость от пачки 6 подтвердилась: конфликтов по
функциональности не было, только по общим файлам и по номерам.

## Найдено попутно

Дефекты, обнаруженные при выполнении этой задачи. Не чинил — вне списка
«Что сделать» для `14-clipboard-files.md`.

- **`docs/adr/0036-*.md` отсутствует, хотя номер процитирован.**
  `docs/adr/0035-the-export-reaches-the-user.md` (строка ~123), `e2e/ci-
  stand.sh` (строка 3) и `e2e/smoke.toml` (строка 13) ссылаются на «ADR
  0036» применительно к `e2e/ci-stand.sh`, но файла с этим номером в
  `docs/adr/` нет — каталог перескакивает с `0035` на `0037`. Это ровно тот
  случай, для которого написан раздел «Numbering» в `docs/adr/0001-record-
  architecture-decisions.md`: номер уже процитирован, значит не свободен, и
  листинг каталога вводит в заблуждение. Нужно либо дописать
  `docs/adr/0036-*.md`, либо завести туда «void»-заглушку по образцу ADR
  0021/0022. (Это ровно то же наблюдение, которое, по всей видимости,
  независимо всплыло бы и при выполнении `10-clipboard-auto.md` — см. ADR
  0046 «Что оказалось на самом деле» выше.)
- **`capabilities-pilot/main.json` отстаёт от `capabilities/main.json`.**
  У `capabilities-pilot/main.json` нет `allow-history-remove`,
  `allow-connect-cancel` и `allow-connection-stats`, которые есть в
  `capabilities/main.json` — то есть pilot-сборка (`--features pilot`)
  вызвала бы эти команды из главного окна и получила бы отказ, которого нет
  в обычной сборке. Не трогал: расхождение существовало до этой задачи и не
  входит в список файлов `14-clipboard-files.md`.
