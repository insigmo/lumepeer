# 16 — Смена физического режима экрана хоста

**Зависимости:** `13` (разрешение потока). Пачка 11, последняя.

Решение принято, см. `DECISIONS.md`, **D7**, пункт 2. Это фича, а не
багфикс.

**Файлы:**
- `crates/media/src/capture/windows.rs`, `crates/media/src/capture/linux_x11.rs`
- `crates/media/src/capture/mod.rs`
- `crates/core/src/protocol.rs`, `crates/core/src/constants.rs`
- `apps/desktop/src-tauri/src/network.rs`, `apps/desktop/src-tauri/src/commands.rs`
- `apps/desktop/src/toolbar.ts`, `apps/desktop/src/i18n.ts`
- `docs/adr/` — новый ADR

## Симптом со слов пользователя

«расширить выбор разрешений, который доступен у подключенного хоста. То есть
когда устанавливается люмпир, тогда нужно будет сохранить список разрешений
экрана, что доступно и там сохранить. При каждой новой установке или
обновлении, нужно запрашивать заново… Когда кто то подключается к тебе, у
него в настройках есть выбор разрешений, вот туда прокинуть эти данные каждый
раз при подключении»

## Что делаем и чего не делаем

Здесь хост **физически переключает режим монитора**. Это не то же, что `13`
(разрешение потока) — и это заметно рискованнее: смена режима двигает окна
пользователя, а на некоторых конфигурациях необратима без ручного
вмешательства.

**Платформы:**

| ОС | API | Статус |
|---|---|---|
| Windows | `EnumDisplaySettingsW` / `ChangeDisplaySettingsExW` | делаем |
| Linux, X11 | XRandR (`x11rb` уже в зависимостях) | делаем |
| Linux, Wayland | — | **невозможно** без прав композитора (ADR 0010) |
| macOS | `CGDisplayMode` | не в этой итерации |

На платформах, где это невозможно, гость обязан получить **честный пустой
список и объяснение**, а не пустой селект, который молча ничего не делает.
Это ровно тот дефект, который породил исходную жалобу.

## Про «собирать при установке»

Формулировка ТЗ просит собрать список при установке и обновлении и хранить
его у себя. **Так делать не надо**, и вот почему:

- список режимов меняется при подключении монитора, при смене монитора, при
  смене драйвера — то есть между установками, а не при них;
- закешированный на этапе установки список станет врать в первый же день;
- перечисление режимов стоит миллисекунды, кешировать нечего.

**Правильно:** хост перечисляет режимы **при подключении гостя**, как и
просили в последнем предложении («каждый раз при подключении»), и отдаёт
список в ответ на запрос. Это то же самое поведение, что у `monitors_list`.

Если по итогам замера окажется, что перечисление режимов заметно тормозит, —
кешировать в памяти процесса с инвалидацией по событию смены дисплея, но не
на диске и не при установке.

## Что сделать

### Задача 1 — Перечисление режимов

1. Расширить трейт `ScreenCapturer` (`crates/media/src/capture/mod.rs`)
   методом перечисления режимов текущего монитора: ширина, высота, частота.
2. Windows и X11 — реальные реализации. Wayland и macOS возвращают пустой
   список, **не заглушку из выдуманных значений**.
3. Дедупликация и сортировка: список из пятидесяти режимов с одинаковым
   разрешением и разной частотой бесполезен человеку.
4. Ограничение на длину списка — константа в `crates/core/src/constants.rs`.

### Задача 2 — Протокол и IPC

1. Запрос списка режимов и запрос смены режима — по правилам из
   `docs/tasks/03-file-transfer.md`, задача 1: `FEATURE_*` бит, отправка
   только объявившему пиру, валидация на приёмной стороне, отрицательный тест.
2. Хост перепроверяет грант перед сменой режима. **Какой именно грант — это
   решение, а не деталь.** `view` для этого недостаточно: смена режима
   экрана меняет рабочее место человека, а не только картинку у гостя.
   Рекомендация: новый независимый грант, deny by default, как в `15`.
   Зафиксировать в ADR.
3. IPC-команды `host_display_modes` и `host_display_set_mode` — регистрация
   в `invoke_handler` **и** в `capabilities/view.json`. Поля в snake_case.

### Задача 3 — Обратимость

Смена режима должна быть отменяемой:

1. Запомнить исходный режим при первой смене.
2. Восстановить его при завершении сессии — **всегда**, включая аварийное
   завершение. Это `Drop` или явная очистка в том же месте, где закрывается
   всё остальное состояние сессии.
3. На Windows использовать двухшаговое подтверждение
   `ChangeDisplaySettingsEx` (тестовое применение перед постоянным), чтобы не
   оставить человека с чёрным экраном.
4. Тайм-аут авто-возврата: если после смены хост не подтвердил, что видит
   картинку, вернуть исходный режим. Константа с обоснованием.

**Это самая важная задача файла.** Фича, которая может оставить человека с
неработающим монитором, не должна существовать без отката.

### Задача 4 — UI

В тулбаре — второй селект рядом с тем, что делает `13`, с ясным
разграничением:

- «Разрешение картинки» (из `13`) — меняет только то, что видит гость;
- «Разрешение экрана хоста» — меняет монитор на той стороне, с
  предупреждением в подписи.

Когда список пуст (Wayland, macOS, нет гранта) — селект показывает причину, а
не пустоту.

Ключи i18n в `en` и `ar`.

## Чего делать НЕ нужно

- **Не кешировать список режимов на диске и не собирать его при установке.**
  Причина выше.
- **Не выдумывать режимы для платформ, где их нельзя перечислить.**
- **Не менять режим по гранту `view`.**
- **Не оставлять смену режима без отката.**
- **Не смешивать с `13`.** Две разные ручки, два разных селекта, два разных
  протокольных сообщения.
- Не браться за macOS в этой итерации.
