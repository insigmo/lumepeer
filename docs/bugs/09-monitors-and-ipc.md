# 09 — Мониторы и рассогласование IPC-контракта

**Зависимости:** нет.

**Пачка 2**, первой в пачке: она чинит контракт, на который опираются `07` и
`13`. Решения по разрешению — в `DECISIONS.md`, **D7**.

**Файлы:**
- `apps/desktop/src/toolbar.ts`
- `apps/desktop/src/file-transfers.ts`
- `apps/desktop/src-tauri/src/commands.rs`
- `apps/desktop/src-tauri/src/network.rs`
- `crates/media/src/capture/*`
- `apps/desktop/src/i18n.ts`

## Симптомы со слов пользователя

1. «Изменение разрешения не происходит»
2. «расширить выбор разрешений, который доступен у подключенного хоста. То
   есть когда устанавливается люмпир, тогда нужно будет сохранить список
   разрешений экрана, что доступно и там сохранить. При каждой новой
   установке или обновлении, нужно запрашивать заново. Имеется ввиду не
   спрашивать у пользователя, а просто получить эти данные и сохранить где
   нибудь у себя. Когда кто то подключается к тебе, у него в настройках есть
   выбор разрешений, вот туда прокинуть эти данные каждый раз при
   подключении»

## Корневые причины

Здесь **три отдельных бага**, и первые два — одного типа.

### 1. `monitors_list` вызывается с неправильной формой аргументов —
**подтверждено**

Rust (`commands.rs`):

```rust
pub async fn monitors_list(
    window: Window,
    state: tauri::State<'_, AppState>,
    peer: String,
) -> Result<Vec<MonitorDto>, IpcError>
```

Параметр называется `peer`.

TypeScript (`toolbar.ts`):

```ts
return (await invoke('monitors_list', { args: { peer } })) as MonitorDto[];
```

Отправляется ключ `args`, а Tauri ищет `peer`. Вызов **всегда падает**.
`openPopover('monitors')` ловит ошибку в `.catch(...)` и показывает пустую
подсказку «нет мониторов». Список мониторов не работал никогда.

Для сравнения, правильно вызываются `chat_transcript`, `clipboard_pull` и
`file_offer` — они тоже принимают `peer: String` и вызываются как
`{ peer }`.

### 2. `monitor_select` шлёт `monitorId` вместо `monitor_id` —
**подтверждено**

Rust (`commands.rs`):

```rust
pub struct MonitorSelectArgs {
    pub peer: String,
    pub monitor_id: u32,
}
```

У структуры **нет** `#[serde(rename_all = "camelCase")]`. Tauri приводит к
snake_case имена **параметров команды**, но не поля вложенных структур — их
разбирает обычный serde.

TypeScript (`toolbar.ts`):

```ts
return invoke('monitor_select', { args: { peer, monitorId } });
```

Поле не совпадает. Выбор монитора **никогда не срабатывал**.

### 2b. Тот же баг в `file_abort` — **подтверждено, найдено попутно**

`FileAbortArgs { peer: String, transfer_id: u64 }` против
`invoke('file_abort', { args: { peer, transferId } })` в
`apps/desktop/src/file-transfers.ts`. Отмена передачи файла молча не
работает.

### 3. Выбор разрешения — заглушка, уехавшая в релиз — **подтверждено**

`toolbar.ts`:

```ts
export const RESOLUTION_CHOICES: readonly string[] = ['native', '1080p', '720p'];
...
setResolution(value: string): void {
  // Placeholder by design (§11): the choice is recorded so the real
  // implementation can pick it up, but nothing is sent to the host yet.
  if (RESOLUTION_CHOICES.includes(value)) {
    state.resolution = value;
  }
  draw();
}
```

Селект есть, значение запоминается в поле объекта и **никуда не уходит**. Ни
IPC-команды, ни протокольного сообщения для смены разрешения не существует —
`grep` по `resolution` в `crates/` это подтверждает.

### Почему это не поймали тесты

`toolbar.test.ts` подставляет фейковый `ToolbarCommands`. Фейк соответствует
TypeScript-интерфейсу, а не реальному контракту Rust-команды. Оба
рассогласования выше проходят мимо тестов по построению. Это надо закрыть
отдельно — задача 3.

## Что сделать

### Задача 1 — Починить три вызова IPC

1. `toolbar.ts`, `monitorsList`: `invoke('monitors_list', { peer })`.
2. `toolbar.ts`, `monitorSelect`: `invoke('monitor_select', { args: { peer,
   monitor_id: monitorId } })`. Имя поля в объекте — **snake_case**,
   переменная в TS может остаться `monitorId`.
3. `file-transfers.ts`, `fileAbort`: `{ args: { peer, transfer_id:
   transferId } }`.

Альтернатива для пунктов 2 и 3 — навесить `#[serde(rename_all =
"camelCase")]` на Rust-структуры. **Не делать так**: в проекте уже принят
snake_case на границе IPC (`since_us`, `since_seq`, `code_required`,
`at_unix` — все snake_case), и разнобой хуже, чем один стиль.

→ **Проверка:** вручную с хостом на нескольких мониторах — попап показывает
список, выбор переключает картинку. Отмена передачи файла останавливает
передачу.

### Задача 2 — Убедиться, что серверная часть выбора монитора работает

После задачи 1 впервые заработает путь, который раньше никто не проходил.
Проверить, что `network.rs::monitors_list` и обработчик `monitor_select`
действительно доходят до бэкенда захвата и что смена монитора приводит к
новому кадру с другим размером. Если там тоже есть дефекты — они станут
видны только сейчас.

Особое внимание: `view.ts::tick` уже умеет обрабатывать смену разрешения
кадра посреди сессии (`if (frame.width !== frameSize.width ...)`), так что
со стороны гостя всё должно быть готово.

→ **Проверка:** интеграционный тест в `network.rs` (там уже есть двухузловые
тесты): после `monitor_select` хост начинает отдавать кадры другого размера.

### Задача 3 — Защита от повторения рассогласования (**обязательно**)

Один и тот же дефект встретился трижды. Нужен барьер, а не три точечных
фикса.

Варианты, в порядке предпочтения:

- **A.** Rust-тест, который для каждой команды из
  `main.rs::invoke_handler` проверяет, что её аргументы разбираются из
  JSON, который реально шлёт фронтенд. Требует места, где эти JSON записаны,
  — то есть фикстур.
- **B.** Генерировать типы IPC из Rust (`ts-rs`, `specta`) и заставить
  фронтенд вызывать команды через сгенерированные обёртки, а не через строки.
  Решает проблему на корню, но это большая правка — **только по отдельному
  решению**.
- **C.** Скрипт проверки в CI: парсит `invoke('name', {...})` в
  `apps/desktop/src/**/*.ts` и сверяет ключи верхнего уровня и полей с
  сигнатурами `#[tauri::command]` в `commands.rs`.

**Рекомендация: C.** Дёшево, ловит ровно этот класс ошибок, не требует
менять архитектуру. Положить в `ci/` рядом с `resource-budget.yml` и
подключить к тому же прогону.

Минимум, если C окажется дороже ожидаемого: **добавить к каждой команде в
`commands.rs` doc-комментарий с примером вызова из TS**, и в ревью-чеклист —
сверять. Это слабее, но лучше, чем ничего.

→ **Проверка:** проверка падает, если вернуть один из трёх багов задачи 1.

### Задача 4 — Убрать заглушку выбора разрешения из тулбара

Настоящий выбор разрешения делается в `13-stream-resolution.md` (решение
**D7**). Здесь надо только убрать неработающий контрол, чтобы он не дожил до
следующего релиза:

- удалить `RESOLUTION_CHOICES`, поле `ToolbarState.resolution`, действие
  `setResolution` и селект из `settingsPopover`;
- удалить ключи `toolbar.settings.resolution` и `toolbar.resolution.*` из
  `en` и `ar`;
- поправить шапку `toolbar.ts`: она описывает выбор разрешения как
  «placeholder for now», чего больше не будет.

`13` вернёт селект — но уже рабочим, и с другим списком значений. Оставлять
нерабочий контрол «чтобы не переделывать» не надо: именно он и породил
жалобу.

Если `13` делается сразу следом и в той же ветке — эту задачу можно
пропустить, отметив это в отчёте. Во всех остальных случаях — делать.

## Что оказалось на самом деле (задача 2)

Задача 2 предполагала проверку. Проверка нашла третий баг, крупнее первых
двух: **вся серверная часть выбора монитора была написана не на той
стороне.**

Окно просмотра существует только у гостя (`view.rs::open` вызывается из
`start_view`), и обе IPC-команды закрыты `check_view_window`. То есть
вызывает их всегда гость. А в акторе они шли в host-side обработчики:

- `on_monitors_list` перечисляла `crate::view::host_monitors()` — мониторы
  **той машины, на которой запущено окно**, то есть гостевые, — и отправляла
  их хосту сообщением `MonitorsList`. Направление обратное.
- `on_monitor_select` дёргала `set_target` у **гостевого** захвата.
- Входящее `MessageKind::MonitorsList` гость не обрабатывал вообще: арма в
  `match` не было, список хоста было некуда положить.
- `on_monitors_list` к тому же требовала `sessions.state(peer) == Active` —
  host-side сессию, которой у гостя нет, — так что после фикса аргументов
  вызов всё равно возвращал бы `UnknownPeer`.

Сделано (без нового протокольного сообщения — его в ADR 0028 нет, и заводить
его здесь нельзя):

1. Хост объявляет `MonitorsList` в `grant_role`, там же, где `add_viewer` и
   `announce_media_fault`: гостю нечем спросить, значит объявление и есть
   единственный способ отдать список. Хост без захвата (`health.fault()`) не
   объявляет ничего — пустой список честнее выдуманного.
2. Гость складывает пришедший список в `ViewState.monitors`.
3. `monitors_list` у гостя читает этот список (`on_announced_monitors`).
4. `monitor_select` у гостя отправляет `MessageKind::MonitorSelect`
   (`on_pick_monitor`), предварительно проверив, что такой id объявлялся.
   Обработчик на хосте уже был написан и работает.

Заодно снят гейт `if self.media.contains_key(&peer)` вокруг обработки
входящего `MonitorSelect` на хосте. Авторизует грант `view`, и его проверяет
`on_monitor_select`; захват уже идёт с момента гранта. Гейт молча ронял выбор,
сделанный в окне переподключения медиа, — после чего возвращалась картинка с
того монитора, с которого оператор только что ушёл (§18).

Тест: `network.rs::the_guest_picks_a_screen_and_the_host_is_the_one_that_moves`.
На машине, которая не умеет перечислять дисплеи (сборка под Windows без
`capture-windows`), он проверяет вторую половину: список пуст и выбор
отвергается — но не подменяется собственными экранами. Полная ветка проходит
на Linux (CI) и на Windows с `--features capture-windows`.

**Чего проверить не удалось:** что после смены монитора хост отдаёт кадры
другого размера. Для этого нужны два физических монитора разного разрешения и
живой медиа-тракт; в `cargo test` гостевой декодер — отдельный процесс
(ADR 0019), которого там нет. Тест проверяет то, что доказуемо в этой
обвязке: выбор доезжает до `CaptureController::set_target` на хосте. Смена
размера кадра — путь, который уже покрыт со стороны гостя (`view.ts::tick`).

## Чего делать НЕ нужно

- **Не навешивать `rename_all = "camelCase"` на Rust-структуры аргументов.**
  Правится сторона TS.
- **Не «чинить» тесты тулбара так, чтобы они начали проверять IPC.** У них
  другая задача — проверять состояние тулбара. Барьер строится отдельно
  (задача 3).
- **Не реализовывать выбор разрешения здесь.** Это `13`, отдельная задача с
  новым протокольным сообщением.
- **Не оставлять неработающий селект разрешения.** Либо `13` делается сразу
  следом, либо селект снимается.
- **Не менять `MonitorDto`** — он корректен и уже несёт `width`/`height`, что
  пригодится для подписи вариантов.
- **Не трогать `ABR_MIN_SCALE_PERCENT` и ступени ABR.** Это `13`.

## Definition of done

- [ ] Список мониторов открывается и показывает реальные мониторы хоста.
- [ ] Выбор монитора переключает картинку.
- [ ] Отмена передачи файла работает.
- [ ] Есть барьер, который ловит рассогласование IPC-контракта; он падает,
      если вернуть любой из трёх багов.
- [ ] Заглушка выбора разрешения снята с UI (или сразу заменена работающей
      реализацией из `13`).
- [ ] Комментарий в шапке `toolbar.ts` про «placeholder for now» приведён в
      соответствие с реальностью.
- [ ] Все проверки из `docs/bugs/README.md` пройдены.

## Найдено попутно

- Шапка `toolbar.ts` описывает выбор разрешения как временную заглушку. Это
  не так — заглушка в релизе. Комментарий поправить в рамках этой задачи.
- Корневой `README.md`, раздел «Status», утверждает, что фазы 0–6 §19
  закрыты. Как минимум выбор монитора не работал вообще. После этой задачи
  формулировку стоит перепроверить — но правит её отдельная задача, не эта.
- `apps/desktop/src/toolbar.ts` вызывает `file_offer` как `{ peer }`, а
  `apps/desktop/src/file-transfers.ts` — тоже `{ peer }`. Обе верны; сверить
  их с барьером из задачи 3, чтобы он не дал ложное срабатывание.
