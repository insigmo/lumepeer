## 1. Кнопка Close неактивна

### Что происходит сейчас (проверено по коду)

`terminalChrome` в `apps/desktop/src/terminal.ts` рисует кнопку так:

```ts
?disabled=${status !== 'open'}
```

То есть кнопка активна **только** пока оболочка запущена. Во всех остальных
состояниях — `idle`, `opening`, `closed`, `refused` — она серая. Именно
`refused` пользователь и видит в пункте 2: хост отказал, кнопка мертва, и
закрыть нечем.

Второе: обработчик — `session.close()` (`mountTerminal`, там же), а это
«убить оболочку», **не** «закрыть терминал». Даже в активном состоянии кнопка
не делает того, что обещает её имя.

Окно у терминала уже своё (ADR 0101): `view_windows.rs::open` открывает
`view.html?peer=..&host=..&input=0&terminal=1`, а `view.ts::main` в этом
режиме прячет канвас и разворачивает панель на всё окно. Закрытие окна уже
делает всё правильное — `onCloseRequested` в `view.ts` останавливает
терминал и завершает сессию.

### Что сделать

**Задача 1.1.** Кнопка активна всегда: убрать `?disabled` из
`terminalChrome`. Состояние показывает `term-state`, а не доступность кнопки.

**Задача 1.2.** Кнопка закрывает терминал, а не только оболочку. Поведение
зависит от того, что это за окно, поэтому действие приходит **снаружи**:
`mountTerminal` получает новый параметр `onClose: () => void`, а решение
принимает `view.ts`:

- **Терминальное окно** (`terminalOnly === true`): `session.close()`, затем
  `getCurrentWindow().close()`. Дальше всё уже делает `onCloseRequested`.
- **Окно с картинкой**: `session.close()`, затем `terminalPanel.hidden = true`
  — ровно то, что делает `toggleTerminal` в обратную сторону. Тулбар потом
  открывает панель заново, и `openTerminal` поднимает новую оболочку.

В обоих случаях сначала `session.close()`, и только потом закрытие: процесс на
чужой машине, переживший окно, — тот исход, который ADR 0079 запрещает.

**Задача 1.3.** Тесты в `terminal.test.ts`: кнопка не `disabled` ни в одном из
пяти состояний; клик в состоянии `refused` вызывает `onClose`; клик в
состоянии `open` сначала шлёт `terminal_close`, потом зовёт `onClose`.

### Чего НЕ делать

- Не переименовывать кнопку и не добавлять вторую («Close shell» / «Close
  window»). Пользователь просил одну работающую кнопку.
- Не трогать `TerminalSession.close()` — там `#shell === null` корректно
  возвращает `Promise<void>`, и вызов на закрытой сессии уже безопасен.

## 2. «The host refused … could not run the shell as the person sitting at
that machine»

### Что это за сообщение

Это `TerminalRefusal::CannotDropPrivileges`. Полный путь, сверху вниз:

`apps/desktop/src/locales/en.ts` → `terminal.refused.cannotDropPrivileges` ←
`terminal.ts::REFUSAL_KEYS[5]` ← `crates/runtime/src/network.rs:3441`
(`TERMINAL_EVENT_REFUSED_CANNOT_DROP`) ← `network.rs:7394`
(`ShellError::CannotDropPrivileges → TerminalRefusal::CannotDropPrivileges`) ←
`Shell::spawn` в `crates/terminal/src/lib.rs` ← платформенный бэкенд.

Оболочку запускает **сам процесс приложения-хоста**
(`on_terminal_open_request` зовёт `Shell::spawn` прямо на петле актора), а не
служба.

ADR 0079 запрещает откат: если понизить права не удалось, процесс **не
создаётся вообще**. Сообщение честное — вопрос в том, почему не удалось.

### Причина: три кандидата, ни один не проверен

**Гипотеза A — Windows-хост, `CreateProcessAsUserW` отказала (наиболее
вероятная).** `crates/terminal/src/windows.rs::interactive_user_token` берёт
токен процесса за `GetShellWindow()` (Explorer) и дублирует его как primary;
`spawn_shell` зовёт `CreateProcessAsUserW`. Клиент по ADR 0057 всегда
запускается с `requireAdministrator`. Токен администратора содержит
`SE_INCREASE_QUOTA_NAME` в **выключенном** состоянии и не содержит
`SE_ASSIGNPRIMARYTOKEN_NAME` вовсе — а `CreateProcessAsUserW` требует первую
привилегию всегда и вторую в части случаев. Классический исход —
`ERROR_PRIVILEGE_NOT_HELD` (1314).

`CreateProcessWithTokenW`, которой хватило бы `SE_IMPERSONATE` (она у
администратора есть), **не подходит**: она игнорирует `lpAttributeList`, а
`ConPTY` ребёнку передаётся именно списком атрибутов. Это уже записано в
шапке `windows.rs` и менять это решение нельзя.

**Гипотеза B — хост работает как служба (session-0 / unattended).** Тогда
`GetShellWindow()` возвращает ноль, `interactive_user_token` отказывает на
первом же шаге с `reason = "no shell window"`. Для этого случая правильный
механизм — `WTSQueryUserToken`, ровно то, что уже делает
`crates/service/src/agent_launch.rs` из `LocalSystem`.

**Гипотеза C — Unix-хост под `root`.** `unix.rs::may_lend_privileges`
возвращает `false` при `euid == 0`, и это намеренно. Если хост запущен из-под
root — сообщение верное и чинить нечего, кроме текста.

### Задача 2.1 — сначала установить, какая гипотеза

**До единой правки.** Обе ветки отказа уже пишут в лог хоста достаточно:

- `interactive_user_token` → `tracing::warn!(reason = …, "refusing a remote
  shell: this process could not take the interactive user's identity …")` —
  поле `reason` называет шаг, на котором сорвалось;
- `spawn_shell` → `tracing::warn!(%error, "refusing a remote shell: the
  interactive user's token was found but the shell could not be started with
  it …")` — `error` несёт код Win32.

Воспроизвести на хосте, взять лог, записать в этот файл раздел «Что оказалось
на самом деле» с точным кодом ошибки. На Windows лог живо читается только
разделяемым доступом — обычный `Get-Content` покажет 0 байт (см.
`feedback_windows_open_log_reads_as_zero_bytes`).

Дальше — только та ветка, которую лог подтвердил.

### Задача 2.2 — если гипотеза A (1314 / `ERROR_PRIVILEGE_NOT_HELD`)

Самое дешёвое, что может оказаться достаточным: включить
`SE_INCREASE_QUOTA_NAME` в токене своего процесса перед вызовом
(`OpenProcessToken(TOKEN_ADJUST_PRIVILEGES)` + `AdjustTokenPrivileges`), и
только потом `CreateProcessAsUserW`. Привилегия в токене администратора
присутствует, просто выключена; токен Explorer'а — связанный токен того же
пользователя в той же сессии входа, так что `SE_ASSIGNPRIMARYTOKEN_NAME`
может и не понадобиться.

Проверять именно так: включили → вызвали → записали код. Если после этого всё
ещё 1314 — переходить к 2.3, а не подбирать флаги.

Правило ADR 0079 не меняется: `AdjustTokenPrivileges`, который не сработал,
не даёт права запустить оболочку с собственным токеном. Отказ остаётся
отказом.

### Задача 2.3 — если A не лечится включением привилегии, или подтвердилась B

Запуск через службу. У `LocalSystem` есть и `SE_ASSIGNPRIMARYTOKEN_NAME`, и
`SE_TCB_NAME`, и `WTSQueryUserToken` — всё, чего не хватает клиенту.
`crates/service/src/agent_launch.rs` уже делает этот запуск для агента сессии,
включая `CreateEnvironmentBlock`.

Это **отклонение от ADR 0079** (там оболочку запускает клиент) и требует ADR
**0102**. В нём должно быть сказано ровно:

- что именно служба создаёт — `ConPTY` у себя и гонит байты обратно по
  существующему каналу, или запускает маленького воркера от имени
  интерактивного пользователя, который и владеет `ConPTY`;
- как каналы ввода-вывода переживают границу процессов;
- почему это не расширяет права гостя: событие уже прошло
  `terminal_allows(&peer)` в `on_terminal_open_request`, служба не принимает
  решений (тот же довод, что в `crates/host/src/input.rs`);
- что происходит, когда службы нет — остаётся сегодняшний честный отказ.

**Не начинать 2.3, не показав человеку лог и выбранный вариант.** Это
большая правка привилегированного пути, и она не должна быть побочным
эффектом пачки про кнопку.

### Задача 2.4 — если гипотеза C

Ничего не чинить. Дописать в `crates/terminal/src/unix.rs` строку лога, прямо
называющую «клиент запущен от root», и на этом всё: поведение намеренное.

### Чего НЕ делать

- **Никакого отката на собственный токен процесса.** Это ровно тот исход,
  ради предотвращения которого существует `crates/terminal`.
- Не добавлять третий вариант `ShellError`. Гостю нечего сказать сверх двух
  существующих (§15), а детализация — факт о машине хоста.
- Не менять текст перевода, пока не известна причина.

## Что оказалось на самом деле (2026-09-22)

### Пункт 1 — сделано

`?disabled` убран из `terminalChrome`, `mountTerminal` принимает `onClose`,
`view.ts::closeTerminal` выбирает между закрытием окна и прятанием панели.
Три новых теста в `terminal.test.ts`; порядок «сначала `terminal_close`,
потом `onClose`» проверен тем, что при перестановке тест краснеет.

### Пункт 2 — **гипотеза A подтверждена, задача 2.2 опровергнута тем же прогоном**

**Чей это лог.** Логи на этой машине (`DESKTOP-EFHI52Q`) — *гостевые*:
`"a shell was refused"` пишет `on_terminal_open_response`
(`network.rs:7500`), то есть сторона, которая просила. Отказ повторился в
трёх сессиях:

| лог | время (UTC) | peer |
| --- | --- | --- |
| `lumepeer-2026-09-17-091905.log:24-26` | 09:20:40, 09:21:13, 09:21:27 | `c22d0d651097cb29` |
| `lumepeer-2026-09-19-000144.log:139` | 09:07:42 | `63280fa72b884a38` |
| `lumepeer-2026-09-21-100613.log:157` | 10:08:17 | `0d7e71721233fcd9` |

во всех трёх `reason: "CannotDropPrivileges"`. Хост — `beta` (Windows,
tailscale), на момент разбора offline, так что **хостовый лог с полем
`reason=`/`error=` так и не прочитан**.

**Чем он заменён.** Причина оказалась свойством токена, а не машины, и
проверяется где угодно. Скрипт повторяет ровно последовательность
`windows.rs` — `GetShellWindow` → `OpenProcess` →
`OpenProcessToken` → `DuplicateTokenEx` → `CreateProcessAsUserW` — без
псевдоконсоли: `CreateProcessAsUserW` проверяет привилегии до того, как
посмотрит на `lpAttributeList`, поэтому половина с `ConPTY` на ответ не
влияет. Windows 11 Pro 10.0.26200, сессия 1, Explorer на месте
(`interactive_user_token : ok`):

```
                                             не поднят   поднят (RunAs)
CreateProcessAsUserW, привилегии не тронуты      OK          FAILED 1314
enable SeIncreaseQuotaPrivilege                  NOT HELD    ENABLED
CreateProcessAsUserW, после этого                OK          FAILED 1314
enable SeAssignPrimaryTokenPrivilege             NOT HELD    NOT HELD (1300)
CreateProcessAsUserW, после обоих                OK          FAILED 1314
CreateProcessWithTokenW (SeImpersonate)          —           OK
```

**1314 = `ERROR_PRIVILEGE_NOT_HELD`**, ровно как предсказывала гипотеза A.
Три факта из этой таблицы:

1. **Виновата именно элевация.** Тот же код неподнятым проходит. Отказ —
   прямое следствие `requireAdministrator` из ADR 0057, а не поломки на
   `beta`.
2. **Задача 2.2 не помогает.** `SeIncreaseQuotaPrivilege` в поднятом токене
   есть и включается (`ENABLED`), после чего вызов **всё ещё 1314**.
   `SeAssignPrimaryTokenPrivilege` в токене администратора отсутствует
   вовсе — `AdjustTokenPrivileges` отвечает `ERROR_NOT_ALL_ASSIGNED` (1300),
   включать нечего. По правилу самой задачи 2.2 это значит «переходить к
   2.3, а не подбирать флаги».
3. **Клиент всё-таки может запустить процесс от интерактивного
   пользователя.** `CreateProcessWithTokenW` с тем же токеном —
   **OK**: `SeImpersonatePrivilege` у поднятого клиента есть и включена.
   Не хватает не личности, а способа передать ребёнку `ConPTY`.

**Гипотеза B не подтверждена и не нужна:** `GetShellWindow()` отработал,
токен снялся и продублировался; сорвался последний шаг, а не первый.
Замечание на будущее: в гостевом логе каждый отказ окружён строками
`"the host's capture is behind a secure desktop; waiting"` — это про захват
картинки, к токену отношения не имеет, и принимать это за причину не надо.

**Гипотеза C не при чём:** хост — Windows.

### Что из этого следует для 2.3

Оба варианта отклоняются от ADR 0079 (оболочку перестаёт запускать сам
клиент) и требуют **ADR 0102**. Выбор — за человеком, правка
привилегированного пути:

- **D — воркер через `CreateProcessWithTokenW`, без службы.**
  Клиент запускает крошечный воркер от имени интерактивного пользователя
  (одной привилегии `SeImpersonate`, которая у него уже есть, хватает —
  строка `OK` выше). Воркер, будучи уже правильной личностью, сам зовёт
  `CreatePseudoConsole` и обычный `CreateProcessW` для `%COMSPEC%` и гонит
  байты клиенту по трубам. Кросс-личностный шаг ровно один, службы не
  требуется, поведение не меняется на машине без неё.
- **E — запуск через службу (то, что описывает 2.3).** У `LocalSystem` есть
  `SE_ASSIGNPRIMARYTOKEN_NAME`, `SE_TCB_NAME` и `WTSQueryUserToken`, и
  `crates/service/src/agent_launch.rs` уже делает такой запуск. Дороже: даёт
  зависимость от службы и требует честного отказа там, где её нет.

Шапку `windows.rs` в любом случае придётся переписать: сейчас она
утверждает, что `CreateProcessAsUserW` — рабочий путь, а
`CreateProcessWithTokenW` не подходит. Первое неверно для поднятого
клиента, второе верно только про сам `ConPTY`-атрибут, а не про запуск
процесса.

## Что было сделано (2026-09-22, вариант D)

Выбран вариант **D** — воркер через `CreateProcessWithTokenW`, без службы.
ADR **0102** написан. По дороге выяснилось, что отказ был не единственной
поломкой: **терминал на Windows не работал никогда**, и «хост отказал» просто
закрывало собой два других бага, до которых раньше нельзя было дойти.

### Три бага, а не один

**1. Отказ (то, с чего начали).** Поднятый клиент не может
`CreateProcessAsUserW`. Чинится воркером: `CreateProcessWithTokenW` хватает
`SeImpersonate`, воркер уже нужная личность и заводит `ConPTY` обычным
`CreateProcessW`.

**2. `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` получал указатель на `HPCON`, а
не сам `HPCON`.** Было:

```rust
Some(std::ptr::from_ref(&console.0).cast::<c_void>()),
```

`UpdateProcThreadAttribute` при этом возвращает `Ok` — он только запоминает
указатель, — а `CreateProcess` читает по нему мусор и **молча** не
подключает ребёнка к псевдоконсоли. Симптом: `conhost --headless` живой,
`cmd.exe` живой, из трубы приходит **ноль байт**. Проверено на нетронутом
`HEAD`: там ровно то же, 0 байт. То есть даже там, где спавн проходил
(неподнятый клиент), гость всё равно не увидел бы ни символа.

**3. Оболочка наследовала стандартные дескрипторы воркера вместо консольных.**
Стандартные хэндлы воркера — это две трубы клиента. Ребёнок, запущенный без
`STARTF_USESTDHANDLES`, берёт их, а не консоль: баннер `cmd` уезжает прямо в
провод мимо `ConPTY`, а ввод оболочка читает из той же трубы, из которой
воркер читает кадры, — то есть не читает никогда. Симптом после фикса №2:
вывод есть (166 байт), эха нет, команда не выполняется. Лечится тремя
строками, которые `portable-pty` носит с тем же комментарием:
`dwFlags = STARTF_USESTDHANDLES`, все три хэндла `INVALID_HANDLE_VALUE`.

### Чем проверено

`crates/terminal-worker/tests/a_shell_really_starts.rs` — поднимает реальную
оболочку, печатает в неё, ждёт эха, меняет размер и убивает. Один и тот же
тест покрывает обе ветки, и какую именно — решает то, как запущен сам тест:

| | путь | результат |
| --- | --- | --- |
| неподнятый | `CreateProcessW` (та же личность, проверено по SID + elevation) | зелёный |
| поднятый (`RunAs`) | `CreateProcessWithTokenW` с токеном Explorer'а | зелёный |

Вручную, до теста: `echo hi` → эхо посимвольно, `hi`, новый промпт.

### Что ещё изменилось

- `crates/terminal/src/windows.rs` больше не содержит `ConPTY` вообще —
  консоль живёт только в воркере. Один путь, который берут и `cargo test`, и
  установленный клиент; вторая копия была именно тем местом, где баги №2 и №3
  прожили незамеченными.
- `Win32_System_Console` убран из зависимостей `crates/terminal`.
