## Итог работы 2026-08-24 (сквозной прогон через интернет)

### Исправлено

- **Аудио-приёмник гостя больше не открывает второе `rd/media/1`-соединение.**
  В записи от 2026-08-23 (вопрос №9) сказано, что `spawn_media_receiver`
  «запускает `stream_audio_receiver` на каждый медиа-диал» — на деле тот
  диалил **своё** соединение, а хост пишет аудио в то же соединение, что и
  видео (`on_audio_toggle` берёт `session.connection`). Для хоста второй диал
  того же пира = передиал, и `on_media_accepted` заменял медиа-сессию,
  `abort()`-я энкод-луп: видео умирало через доли секунды после старта, гость
  начинал новый проход и спавнил ещё один вечный аудио-приёмник. Картинка не
  доходила никогда, в логе хоста при этом ни одной ошибки (отмену задачи
  никто не логирует). Теперь `stream_once` сначала забирает видео-стрим, а
  затем поднимает `spawn_audio_pass` на **том же** соединении; страж
  `AbortOnDrop` гасит его вместе с проходом. Тест:
  `view::tests::one_media_pass_dials_one_connection`.
- **Первый кадр на Windows** берётся GDI-снимком монитора: DXGI Desktop
  Duplication не отдаёт ничего до первого present'а, а статичный рабочий стол
  может не презентовать минутами (`crates/media/src/capture/windows.rs`,
  `gdi_snapshot()` + `awaiting_first_frame`).
- Проверено вживую: хост `beta` через интернет (Iroh/QUIC), роль `view_only`,
  одно медиа-соединение, окно просмотра показывает удалённый рабочий стол и
  обновляется.

### Осталось открытым

- `awaiting_first_frame` взводится в `ScreenCapturer::start()` (первый
  зритель), а не на каждую медиа-сессию: после передиала посреди сессии новый
  энкод-луп снова ждёт present'а вместо снимка. Нужен способ перевзвести
  «первый кадр» на новую медиа-сессию.
- Устройство вывода звука у гостя всё ещё не подключено:
  `std::mem::forget(pcm_rx)` в `spawn_media_receiver` — заглушка.

## Итог работы 2026-08-23 (сессия catch-up, вторая волна)

### Сделано (реализовано и протестировано)

- **Чат в главном окне хоста**: кнопка Chat у каждой активной сессии в списке,
  шторка `#host-chat-panel` переиспользует компонент `chat.ts` из окна
  просмотра; авто-закрытие при завершении сессии. Ключи i18n (`chat.open`,
  `chat.close`, en/ar), стили, vitest-пиннинг (`host-chat.test.ts`). Полный
  фронтенд-набор зелёный: 7 файлов, 63 теста + typecheck.
- **Аудио: захват** (решение №8 — платформенные API напрямую, не cpal):
  трейт `AudioCapturer` + фабрика `platform_audio_capturer()` в
  `crates/media/src/capture_audio.rs`; WASAPI-loopback за фичей
  `audio-capture` (shared-mode, только IEEE-float микс, иначе громкий отказ),
  PipeWire-monitor за `audio-capture-pipewire`. Ресемплинг в wire-format
  (48 кГц s16 stereo) в одном месте — `to_wire_pcm`. Тесты зелёные.
- **Аудио: проводка через net**: тегированные uni-streams на `rd/media/1`
  (байт-тег `A`/`V` в начале потока; видео не тронуто),
  `open_tagged_media_stream` / `accept_audio_media_stream`,
  `encode/decode_audio_payload`. net зависит от media минимально (голый
  `AudioChunk`, без кодек-фич).
- **Аудио: хост-цикл** (`view.rs::spawn_audio_loop`): захват → Opus-энкод →
  тегированный поток; без бэкенда или энкодера — громкий отказ и сессия
  остаётся video-only (§18). Команда актора `AudioOn/AudioOff` c проверкой
  гранта `view`; IPC `audio_toggle` (только главное окно), регистрация в
  build.rs/capabilities (+ пилотные копии).
- **Аудио: воспроизведение у гостя** (решение №9): `spawn_media_receiver`
  запускает `stream_audio_receiver` на каждый медиа-диал; декодирование Opus
  в процессе гостя (libopus сам валидирует недоверенный битстрим, worst case
  — шум, §11.3 сохранён для видео), PCM уходит в watch-канал для устройства
  вывода. Хост молчит — приёмник паркуется и ретраится (аудио можно включить
  посреди сессии).
- **Интеграция записи LMRC** (вопрос №7 доведён до конца):
  `apps/desktop/src-tauri/src/recorder.rs` — `SessionRecorder`: поток-писатель
  за bounded-очередью (медиа-циклы никогда не блокируются о диск; переполнение
  = дроп записи с логом, §24.5). Слот `SharedRecorder` в видео- и аудио-циклах:
  запись включается/выключается посреди сессии без перезапуска конвейера.
  Команды актора `RecordOn/RecordOff` с проверкой независимого гранта
  `recording` (§8.2); IPC `recording_toggle`; teardown сессии флашит файл.
- **Clippy чист**: `-p desktop/media/net --all-targets` = 0 варнингов
  (было ~45 после первой волны аудио-работы); fmt чист.

### Не сделано / вне этой сессии

1. **E2E на VM упирается в таймауты tauri-pilot eval** (без изменений с
   прошлой сессии): нужен либо vite dev server на VM, либо сборка со
   встроенным frontendDist, либо разбор версий плагина/CLI. Требует доступа
   к Linux-VM по SSH — в этой сессии недоступно.
2. **UI-переключатель записи и звука** в главном окне: IPC-команды готовы
   (`audio_toggle`, `recording_toggle`), осталось повесить кнопки в
   `session-status.ts` рядом с revoke + ключи i18n.
3. **Устройство вывода PCM у гостя**: канал `pcm_rx` наполнен, но реальный
   audio-sink (WASAPI render / PulseAudio) ещё не подключён — следующий
   кандидат на отдельную задачу (за фичей, как захват).

## Решённые вопросы

### 8. Аудио-захват: какой backend брать для каждой ОС? — **решено 2026-08-23**
Платформенные API напрямую за фичами, НЕ cpal: WASAPI loopback (Windows,
shared-mode IEEE-float) и PipeWire monitor дефолтного sink (Linux) дают
loopback системного микса без лишней прослойки; CoreAudio tap (macOS) —
по той же схеме, когда дойдёт руки. Фичи `audio-capture` /
`audio-capture-pipewire`; без них фабрика отказывает громко, сессия
остаётся video-only (§18).

### 9. Воспроизведение у гостя: cpal или через decoder-worker? — **решено 2026-08-23**
Opus-декодирование у гостя — в главном процессе: libopus сам валидирует
недоверенный ввод и отвечает concealment'ом (worst case — шум), а out-of-process
sandbox §11.3 остаётся зарезервирован за видео, где битстрим реально опасен.
PCM идёт в watch-канал; устройство вывода — за фичей, отдельно от кодека.

### Чат хоста — **решено 2026-08-23**
См. итог выше: панель в главном окне, переиспользование `chat.ts`.

### Интеграция записи — **решено 2026-08-23**
См. итог выше: писатель в живом конвейере, грант `recording`, IPC готов;
кнопка в UI — косметика (см. «Не сделано» №2).

### 1. Аудио: какой кодек Opus-крейт брать в воркспейс? — **решено 2026-08-22**
Крейт `opus = "0.3"` (биндинги над libopus), системный SDK не нужен:
`audiopus_sys` вендорит исходники и собирает cmake'ом — тот же прецедент, что
openh264. Фича `audio-opus`; без неё аудио-точки отказывают громко.
Константы: 48 кГц, стерео, 20 мс, 96 кбит/с. Потери → concealment.
ADR 0023. Сборочным хостам нужен cmake на PATH.

### 2. Unattended-пароль: argon2 или PBKDF2? — **решено 2026-08-22**
`argon2 = "0.5"` (RustCrypto), Argon2id; PHC-строка в OS keystore; проверка в
TCB; 5 неудач → lockout 300 с. Соль из workspace CSPRNG через
`SaltString::encode_b64`.

### 3. TOTP 2FA: самим или крейт? — **решено 2026-08-22**
Своя реализация RFC 6238 поверх HMAC-SHA1 (~50 строк) + тесты на векторах
Appendix B (последние 6 цифр опубликованных 8-значных). Окно ±1 шаг.

### 4. Приоритет платформ — **решено 2026-08-22**
Ядро → Windows → Linux → macOS; Wayland последним, отдельная Wayland-VM
(`WAYLANDLINUX_HOST`), E2E по SSH на обеих Linux-машинах.

### 5. Мобильные/web клиенты — **решено 2026-08-22**
Отложить до готовности десктопа.

### 6. Relay — **решено 2026-08-22**
Документация + docker-compose для self-host `iroh-relay`; своего кода релея
нет. Плюс клиентский override `LUMEPEER_RELAY_URL`. ADR 0023.

### 7. Запись сессии — **решено 2026-08-22**
Кастомный append-only контейнер «LMRC», MKV-экспорт позже. Заголовок + записи
(видео/Opus/JSON-события), относительные таймстампы, проверки до аллокации,
оборванный файл = валидный префикс. Грант `recording`. ADR 0023.
